# Skill 审计 · 重复性(查重)维度

> 上半部分(背景 / 产品行为 / 判断标准)不涉及技术;"实现细节"及以下是工程向。

## 背景
marketplace 会积累重复/冗余 skill:同一个技能被重复上传,或换个说法解决同一件事。需要识别出来提示,但不能误伤——"同领域不同任务""同问题但更优/互补"的 skill 不算重复。

## 产品行为
- 给每个 skill 算一个"独特性"结果,并列出它疑似重复的其他 skill。
- 只做提示(进评分卡、给作者/管理员看、可建议合并),**不拦截、不下架**。
- 判定分四种,不是简单的"像/不像":
  - 同一个问题 + 方法相同或更差 → 重复
  - 同一个问题 + 明显更好 → 取代(旧的才是多余的)
  - 同一个问题 + 各有所长 → 正当替代,保留
  - 不同问题 → 无关

## 什么算"重复"(判断标准)
从两个角度看一个 skill:
- 解决什么问题(名称、描述、能力说明)。
- 怎么解决、做得好不好(指令、输入参数、子能力、附带代码)。

只有"解决同一个问题,且方法相同或全面更差"才判重复;哪怕解决同一问题,只要各有所长或更优,就不算。判"更差"看几条质量点:场景覆盖、输入是否完整、有无示例与使用规则、指令是否具体(权重由业务定)。
依据:软件工程的代码克隆分类(完全复制 / 改名 / 近似修改 / 语义相同)。

---

## 实现细节

### 方法(两阶段漏斗)
1. 先粗筛候选(确定性,要看全量 skill):算文本相似度 + 比对附带文件,把"可能相关"的成对捞出来,阈值放宽、只筛不判,不会误杀。
2. 再语义裁决(语义节点,只提示):把候选交给语义节点,判上面四种里的哪一种,并做质量对比。语义节点也能补上纯文字相似度看不出的"改写重复"。

### 工具
- 文本相似度:datasketch(MinHash,MIT);附带文件比对:哈希(完全相同)+ copydetect(代码近似克隆)。选 MinHash 而非向量模型,是因为没有可用模型/端点,而当前 24 个量级 MinHash 足够。
- 语义裁决:复用安全维的语义判定器(kiro-cli,model=auto),不硬绑。
- 排除同一个 skill 的版本重传(那不算重复)。

### 实测(24 真实 skill)
- 真重复:一个被重复上传的 skill,两个角度相似度 0.95 / 0.99,附带压缩包字节完全相同——抓到。
- 不误伤:其余所有 skill 两两相似度 ≤0.05;同属射频设计的一组 skill(PCB/天线/TRX/滤波器)没有被误判为重复。
- 边界:轻微改动的复制能抓到(相似度 0.65);整段改写的复制,纯文字比对抓不到(0.00),要靠语义节点补。

### 局限
- 纯文字比对漏"整段改写",靠语义节点补;skill 数量上千时需要换更快的检索方式,现在 24 个不需要。
- "更优/更差"带主观性,语义节点给建议、人工定;因为不拦截,风险低。

### 待确认
1. 独特性结果与"疑似重复"列表在页面怎么呈现。
2. 质量点的权重由业务定(不给也有默认可先跑)。
