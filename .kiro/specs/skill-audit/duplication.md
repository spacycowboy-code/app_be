# Skill 审计 · 重复性(查重)维度

> 状态:**设计稿,尚未实现**。文中"实测"一节是用已入库的 skill 跑出来的,脚本与原始结果都在仓库里,可复现。
> 与另两维的关系:安全合规(`security-compliance.md`,已实现)决定**能不能入库**;数据合规(`data-compliance.md`,设计稿)决定**允不允许放进云**;这一维**不拦截任何上传**,只提示重复。

不涉及技术的同事读到"我们已经定下来的"为止即可,后面是工程细节。

## 这一维要解决什么

marketplace 用久了会攒重复:同一个技能被重复上传,或者换个说法解决同一件事。目标是把疑似重复挑出来给人看,同时不误伤"同领域不同任务"和"同问题但各有所长"的 skill。

## 产品行为

- **不拦截、不下架、不打分。** 只在 skill 详情页列出"疑似重复:与 X",并给出证据(重合度 + 差异摘要)。动作由作者或管理员决定。
- **结论是成对的**,不是某个 skill 的属性:"A 与 B 疑似重复"。页面上看到的列表是从这些成对关系里读出来的。
- 自动判定只回答一个问题:**这两个 skill 是不是在解决同一件事。** "谁做得更好"由人判断,系统只提供差异摘要(见下一节)。

## 什么算"重复"

从两个角度看一个 skill:

| 角度 | 取什么文本 | 回答什么 |
|---|---|---|
| 问题 | 名称 + 描述 | 它解决什么 |
| 方法 | SKILL.md 正文 | 它怎么解决 |

判定沿用软件工程里的代码克隆分类,四型对应四种情形:

| 型 | 情形 | 文字比对能不能发现 |
|---|---|---|
| Type-1 | 完全复制 | 能 |
| Type-2 | 改了名字,正文照抄 | 能 |
| Type-3 | 近似修改(删减、调序、局部改写) | 能 |
| Type-4 | 整段改写,意思相同、用词不同 | **不能**——要靠语义层 |

每一型能测到什么程度,见"实测"一节,数字都是跑出来的。

**"谁更好"不做自动判定。** 场景覆盖是否更全、输入参数是否更完整、有没有示例——这些能列出差异,但把它们加权成一个"更优/更差"的结论,权重是主观的,系统给不出可辩护的答案。所以第一版只给差异摘要,不给优劣结论。这样也避免了"因为算法说它更差就把某人的 skill 标成多余"的情况。

## 我们已经定下来的

**1. 不打分。** 与安全维度一致(那边的假评分已经删掉)。呈现的是"与哪个 skill 疑似重复 + 重合度证据",不是一个综合分值。分数会让人以为存在客观排名,而这里没有。

**2. 事实是成对关系,展示是投影。** 记录 `(a, b, 问题重合度, 方法重合度, 判定, 判定时间, 规则哈希)`,追加写、不修改;详情页的"疑似重复"列表由它派生。这和安全维度同一套模型:能从事实重算的才是投影,重算不出来的就是第二份事实。
把重复性压成单个 skill 的"独特性分数"会立刻出问题——两个 skill 互为重复时,标记谁?按成对关系记录,这个问题不存在。

**3. 不进 `status` 闸门。** 重复不影响上架与可见性,所以误报的代价只是页面上多一条提示。这也是这一维可以用宽松阈值的原因。

**4. 触发时机:上传时算一次,再由已有的对帐器周期重算。** 新 skill 与全量做粗筛(当前 20 个 skill 共 190 对,与拉取文本的网络耗时相比可以忽略),命中候选才调语义裁决。不新增调度器,复用安全维度已经在跑的对帐服务。

**5. 阈值取 0.30,依据实测**:库内正常 skill 之间最高 0.16,最轻的改动复制是 0.77,0.30 落在两者之间,两侧都有两倍以上余量。阈值写在规则文件里,可调。

**6. 先用精确比较,不上 MinHash。** 20 个 skill 的全部 190 对可以直接算,精确 Jaccard 测的是这个量本身,不是它的估计值。等成对比较的耗时进入秒级再引入 LSH/MinHash;判据是实测耗时,不是 skill 数量的猜测。

**7. 版本重传不算重复。** 同一个 skill 的新版本是版本关系,不是重复关系。

## 怎么实现

**两阶段漏斗**

1. **粗筛(确定性,看全量)**:对每一对算问题角度与方法角度的重合度;附件比对用哈希(完全相同)与代码近似克隆检测。阈值宽,只筛不判。
2. **语义裁决(只在候选上跑)**:把候选对交给语义判定器,回答"是否同一件事",并输出差异摘要。判定器复用安全维度那一套(只读、模型钉死为 `claude-sonnet-5`,**不用 `auto`**,判定记录存模型名与规则哈希),不重复搭一套。

**文本处理**:大小写归一、去标点后切词;中文没有空格,按字切,使得中英文落在同一套 shingle 方案里。问题角度用 3-gram(文本短),方法角度用 4-gram。

**报告呈现**:复用现有报告契约的呈现方式——每条疑似重复给出对方 skill、两个角度的重合度、以及差异摘要;通过(无疑似重复)也显示,让作者知道系统查过。

## 实测

脚本 `skill_audit/run_duplication_probe.py`,原始结果 `skill_audit/duplication_probe_results.jsonl`;`--selftest` 跑正对照。

**误伤:库内 20 个 skill,190 对**

| 指标 | 结果 |
|---|---|
| 达到 0.30 阈值的对 | **0** |
| 问题角度最高重合度 | 0.08(PCB 布局设计 ↔ 天线阵列设计,同属射频) |
| 方法角度最高重合度 | 0.16(GateCheck ↔ ManifestCheck,两个工具类 skill) |

同属射频设计的一组 skill(PCB、天线阵列、滤波器与封装、系统架构)没有被判为相关,最高只有 0.08。

**灵敏度:正对照(从库内正文最长的 skill 派生,编辑按句块定义,不受换行影响)**

| 情形 | 方法角度重合度 | 对应克隆型 |
|---|---|---|
| 完全复制 | **1.00** | Type-1 |
| 正文照抄、改名字 | **1.00** | Type-2 |
| 删掉 20% 的句块 | **0.77** | Type-3 |
| 句块顺序打乱 | **0.79** | Type-3 |
| 同一件事、完全换词重写(我们自己写的两份 fixture) | **0.02**(问题角度 0.00) | Type-4 |

结论:文字比对覆盖 Type-1 到 Type-3,与库内正常水位(0.16)之间有明显间隔;**Type-4 是文字比对的盲区**,只有 0.02,必须靠语义层——这个缺口现在是测出来的,不是推测的。

那两份 Type-4 fixture(`skill_audit/dup_fixtures/`)是我们自己写的两个功放增益扫描 skill,用词不重叠;真实上传不会被复制到仓库里。

## 怎么验收

| 测什么 | 通过标准 |
|---|---|
| 误伤 | 库内 skill 两两比较,达到阈值的对为 0(有真重复时除外,需人工确认) |
| Type-1/2 | 完全复制与改名复制的重合度 ≥ 0.95 |
| Type-3 | 删减或调序 20% 后仍 ≥ 0.60 |
| Type-4 | 语义层能判出"同一件事",文字层测到的 0.02 不作为通过条件 |
| 成对关系可重算 | 删掉派生数据后重跑,详情页的疑似重复列表与之前一致 |
| 不影响上架 | 判为疑似重复的 skill,`status` 不变、可见性不变 |

## 边界

- **Type-4 靠语义层,而语义层会判错。** 因为不拦截,判错的代价是页面上一条多余或缺失的提示。
- **"谁更好"不自动判。** 只给差异摘要。
- **附件里的近似克隆只覆盖代码。** 文档、二进制的近似比对不做。
- **跨语言重复不覆盖。** 一个中文 skill 和一个英文 skill 解决同一件事,文字比对是 0,语义层是否能判出来没有测过。
- **规模。** 当前用精确比较;换检索方式的判据是实测耗时,不是预估。
