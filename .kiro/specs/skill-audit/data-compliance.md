# Skill 审计 · 数据合规维度

> 状态:**设计稿,尚未实现**。安全合规维度(`security-compliance.md`)已实现并有实测数据;这一维只有设计与验收标准。
> 依据:RTE LT 2026-06-02 批准的临时数据决定(有效期至 2026 年 9 月)。

上传的 skill 除了"会不会害人"(安全维度),还要判"这份内容允不允许放进云"。不涉及技术的同事读到"我们已经定下来的"为止即可,后面是工程细节。

## 甲方的规定

RTE/RCE 自有或共享的数据,配合 Amazon Q / Kiro 使用**不需要审批**,但三类例外:

| # | 例外 | 说明 |
|---|---|---|
| 1 | 客户与伙伴拥有的数据 | 归属不在我们这边的数据 |
| 2 | 按 ISRA 分类为 **very-high confidential** 的数据 | 公司分类体系的最高一级 |
| 3 | 超出基本商务信息的个人数据 | 允许的只有:姓名、signum、公司邮箱与电话、职位、组织 |

这三类要走 *Data in Cloud Infrastructure Risk Assessment Instruction*,由 **L3 manager 逐案决定**;L3 有权按需另开例外。

两点容易读错:

- **Internal 不是例外。** 公司分类有四级(Public / Internal / Confidential / Very High Confidential),规定点的是最高一级。规定所在的那份材料自己页脚就写着 *Ericsson Internal*。
- **规定管的是"使用",不是"发布"。** 它约束把数据交给 Kiro 处理,没有专门谈把数据放进一个共享的 skill 仓库。这个差别决定了决策第 7 条的取舍。

配套材料(Scalable AI — Way forward, 2026-06-05)写明**逐案治理不可扩展**,所以这一维要把这套判断做成上传流程里可自动执行、可留痕的一步。

## 审计对象:这个 skill 会让什么数据进入 Kiro

skill 是会被反复执行的指令,它影响数据合规有两种形态,两种都审:

| 形态 | 例子 | 影响面 |
|---|---|---|
| 自带数据 | 附件里有客户日志、导出表、客户文档 | 发布一次,所有使用者都能下载 |
| 引导取数据 | 指令写"读取 `~/customer_logs/*.log` 并总结"、"连到生产网元导出参数" | 每个使用者每次运行发生一次 |

第二种是规定的原话所指(*data used with Kiro*),并且在上传时就是可读的文本。安全维度不覆盖它:那边的红线是"读取并外传到**外部地址**",而这里的目的地是 Kiro 本身,属于合规问题而非攻击。

产品前提:**skill 是"怎么做一件事"的指令,不是数据。** 它需要指令、代码和合成示例,不需要真实日志、导出表、客户文档或数据集。

## 结果只有两种

| 结果 | 条件 | 处理 | 上传者看到 |
|---|---|---|---|
| **通过** | 无命中,或该内容在审批白名单里 | 上架;走白名单的在详情页与审计事件标注审批依据 | "数据合规检查通过";带审批的显示依据 |
| **拒绝** | 有命中且不在白名单里 | **不入库**,只留审计记录 | 命中项(位置、原文、怎么改)+ 参考编号 + 内容指纹 |

没有"先入库、等审批"的中间态:数据进了库和 git 仓,共享存储里就已经有它了。放行只有一条路径:管理员按 L3 的审批结果加白名单,见"审批白名单"。

一条命中长这样:

```
数据合规 · 个人数据超出允许范围      拒绝
  位置    logs/drive-test.csv:142
  原文    ...,460019876543210,86138****1234,...
  含义    行首字段是 IMSI(移动用户识别码),随后是手机号;两者都属于超出
          "姓名/signum/公司邮箱与电话/职位/组织"范围的个人数据
  怎么改  删掉这个文件,或用占位符/合成数据替换后重新上传;若这份数据确需
          保留,请携带下面的内容指纹与参考编号申请审批,由管理员加白名单
  依据    RTE LT 2026-06-02 临时数据决定(至 2026-09)
```

## 为什么单独成一维,而不是给安全维度加红线

现有六个检查项(密钥、危险指令、隐藏指令、提示注入、附件安全、其他)问的都是"这个 skill 会不会害人"。数据合规问的是另一件事:

| | 安全维度 | 数据合规 |
|---|---|---|
| 谁决定 | 安全评审人 | 上传者所在组织的 L3 manager |
| 记录在哪 | 我们的复核 MR | ISRA / DICIRA 风险评估 |
| 怎么改 | 删掉恶意内容 | 删除或脱敏后重传,或由管理员按审批加白名单 |
| 规则寿命 | 稳定 | 临时指令,9 月到期,要能独立替换 |
| 中间态 | 有(入库不公开,等复核 MR) | 无(要么上架,要么不入库) |

最后一行的原因:未公开的可疑 skill 没人运行,先存着不扩散;而受限数据一旦进入共享存储就已经扩散。

代码现状:`app/services/skill_audit/` 与 `skill_audit/rules.md` 目前没有任何密级、个人数据或客户数据相关逻辑,`secret` 只管凭据(API key、密码、私钥)。这一维是纯新增,不改动现有判定。

## 查什么:内容与指令,不查归属

三类例外里能被自动看见的只有一部分:

| 规定的例外 | 可用信号 | 精确率 |
|---|---|---|
| very-high confidential | 文档密级标记(页眉页脚、文档属性里的固定字样) | 高——标记由材料所有者自己打 |
| 个人数据超范围 | IMSI / IMEI / MSISDN、私人邮箱域、证件号等有固定格式的标识符 | 中——格式化标识符高,自由文本里的个人信息低 |
| 客户与伙伴数据 | 客户名清单、网元名、小区名 | 低——这些词在正常内容里很常见,误报会远多于真命中 |

**归属检不出来**:一份 RAN 配置,是实验室造的还是从客户网上导出的,内容上无法区分。所以检查落在四条可验证的信号上:

| 检查 | 看什么 |
|---|---|
| 密级标记 | 优先读 Office 文件内嵌的密级标签属性;没有标签的文件再看正文与附件文本里的级别字样 |
| 数据载荷 | 附件是文档或数据集(docx/pptx/xlsx/pdf、大 csv、日志),或正文里出现成批记录 |
| 结构化标识符 | IMSI/IMEI/MSISDN、PLMN(MCC-MNC)、私人邮箱域、证件号格式 |
| 数据来源 | 指令要求读取或发送什么,与 skill 声明的输入是否一致 |

这四条各覆盖什么情形:

| 情形 | 结果 |
|---|---|
| 客户网络配置贴进正文 | 结构化标识符 + 成批记录命中 |
| 附一份标着 Confidential 的客户 PPT | 密级标记命中 |
| 附 5 行合成测试数据 | 不命中(载荷判定看形状与规模) |
| 指令写"去读客户服务器上的日志并总结" | 数据来源命中 |
| 声明"只读使用者粘贴的文本",指令却要求读 `~/customer_logs` | 数据来源命中,证据是两边原文 |
| 使用者自己在会话里粘贴客户数据 | 检不出,属网关侧控制点 |

**输入契约**:skill 要声明它需要哪类输入(使用者当场提供的文本、仓库内的文件、公司内部系统、外部或客户系统),判定器把这份声明与指令正文对照。这个声明与"让上传者声明数据归属"不同:它是接口的一部分,能被指令文本证伪。

## 我们已经定下来的

以下九条不去问甲方,理由写在每条后面。

**1. 两态,不做 pending,不做第三方评审。**
数据类问题"先存着等审批"就是扩散本身;而评审人补不上归属这类信息——一份 CSV 里的 IMSI 是真的还是造的只有作者知道,客户材料能不能用是 L3 走 DICIRA 的判断。

**2. 命中一律拒绝,放行只有一条路:管理员按审批结果加白名单。**
不做作者自清,也不做分类声明或确认勾选:勾"无客户数据"照样能把客户日志传上来,既没拦住数据也没产生证据,而每次上传都要填。

**3. 平台不做审批路由。**
L3 manager 是上传者自己组织里的人,平台不做指派。平台的职责是记录:白名单里存审批人与 DICIRA 引用,不校验引用真伪(外部编号无法核验)。

**4. 客户名单本轮不做。**
只做高精度信号:密级标记、数据载荷形状、结构化标识符。不做客户名、网元名、小区名——库里 20 个 skill 里 16 个是 Radio 产品研发测试类,这些词在其中很常见,会产生大量误报。名单以后到手,加一个规则文件即可。

**5. 密级先读文件内嵌标签,再退回文本词表。**
Office 文档(docx/pptx/xlsx)的密级标签由 Microsoft Purview / AIP 写成自定义文档属性,字段名是标准的 `MSIP_Label_<GUID>_Name`,存在 `docProps/custom.xml` 里(见 Microsoft 官方 MIP 元数据说明)。读属性比扫页眉页脚精确,而且不用猜公司模板;`zipfile` 加 XML 解析就够,不需要额外依赖。没有标签的文件(PDF、纯文本、老格式)再用四级级别词表匹配,词表放在可改的规则文件里。读到标签但级别名不认识,按命中处理。
待确认的组织事实:公司文档是否确实启用了 Purview/AIP 标签。启用则这条检查精度很高;未启用则退化为词表匹配。

**6. 审"指令会让什么数据进来",不审"使用者临时粘贴什么"。**
指令在上传时是可读的文本,属于本维度;使用者在会话里粘贴什么,skill 市场观测不到,属于网关侧。

**7. 带 very-high confidential 标记的材料直接拒绝入库,拒绝文案指向审批流程。**
这一条比规定更严:规定约束的是使用数据,而 skill 仓是共享持久存储,发布等于再分发。按数据最小化与需知原则,共享目录不承载最高密级材料。这个差异向甲方报备,不作为提问。

**8. 库里现有的 skill 全部回扫,只出报告,不自动下架。**
对既有数据套新规则,先测量再决定处置。

**9. 策略带版本与生效期。**
规则文件里写 `policy_id: RTE-LT-2026-06-02` 与 `effective_until: 2026-09-30`;审计记录存策略 id 与哈希(与现有 `rules_hash` 同机制);报告显示判定依据;过期后启动即告警,并且不再自动通过。

误报的代价是拒掉一次正常上传,需要一次管理员往返。因此上线前必须先满足验收里"库内现有 skill 误报为 0"。

## 这一维的审计怎么成立

| | 这一维的答案 |
|---|---|
| 审计对象 | 这个 skill 会让什么数据进入 Kiro:它自带的,加上它指令要求读取或发送的 |
| 审计标准 | 不得携带、也不得引导读取未经批准的客户/伙伴数据、very-high confidential 材料、超范围个人数据。标准写在带版本的规则文件里,不写在代码里 |
| 证据 | 每条命中给位置、原文、含义、怎么改;数据来源类命中另给"声明的输入"与"指令实际要读的东西"的对照 |
| 结论与范围限制 | 通过 / 拒绝,并列出没能审到的部分:读不出文本的附件、超出预算未送审的内容、判定器不可用。这些按命中处理,不当作通过 |
| 可复现 | 判定记录存策略 id、规则哈希、判定模型;对同一版本重跑得到同样结论 |

第四行沿用安全维度"未能核实"的写法:报告要列出自己没看到的部分。

**留痕**

| 事实 | 存在哪 | 能否重算 |
|---|---|---|
| 命中项(位置、原文、类别、严重度) | 审计事件,追加写 | 能——策略 id 与规则哈希已钉住 |
| 上传者身份与时间 | 审计事件 | 能 |
| 判定依据的策略版本 | `policy_id` + `effective_until` + 哈希 | 能 |
| 内容指纹 | 审计事件 | 能 |
| 声明的输入契约与对照结果 | 审计事件 | 能 |
| 白名单条目与每次使用记录 | 白名单表 + 审计事件,追加写 | 能 |
| 当时内容长什么样 | skill 仓的 git 历史 | 能 |

审计做不到三件事:验证 DICIRA 编号真伪;确认 skill 运行时实际读了什么(只能拿声明与指令对照);在没有 SSO 之前确认操作者身份。

## 审批白名单

命中之后唯一的放行通道。流程:上传被拒 → 作者拿参考编号与内容指纹找 L3 走 DICIRA → 管理员在前端按审批结果加一条白名单 → 作者重新上传同一份文件 → 匹配到白名单,上架并标注依据。

| 字段 | 作用 | 定法 |
|---|---|---|
| `content_id` | 匹配键 | sha256(SKILL.md 正文)+ 包内每个成员的 (路径, sha256) 排序后一并哈希。不含 zip 元数据,不含 skill 名字,所以重新打包或改名不会让审批失效 |
| `audit_reference` | 来自哪一次拒绝 | 可追回当时的命中清单 |
| `approver_eid`、`approval_ref`、`reason` | 谁批的、依据哪份 DICIRA 评估、为什么 | 审批要落到具体的人和具体的评估上 |
| `expires_at` | 失效时间 | 默认取策略 `effective_until` 与 90 天中较早者 |
| `created_at`、`revoked_at` | 生命周期 | 只作废,不删除 |
| `skill_name`、`uploader_eid` | 管理员界面显示 | 不参与匹配 |

**匹配条件三个:`content_id` 相同、未过期、未作废。** 不用命中清单做匹配条件,因为语义层有运行间波动(实测:同一批 250 个真实 skill 两次跑出 8.0% 与 10.4% 的命中率),用命中清单会让审批因模型抖动而失效。代价:重新上传时新报出的命中也会一并放行。

不能拿来做匹配键的:

| 不用 | 原因 |
|---|---|
| skill 名字或 id | 等于批准这个名字下以后所有版本 |
| 上传者 | 等于给人永久豁免 |
| 规则或模式(如"这个号段一律放过") | 那是调探测器,改规则文件走 MR,不走白名单 |

每次命中白名单,审计事件里记"经白名单 `<id>` 放行";白名单与使用记录可导出供合规抽查。白名单只清数据合规的命中,安全红线不进白名单。

## 用什么现成的,自己写什么

调研过的备选与取舍(版本与依赖数来自 PyPI 查询):

| 需要 | 用 | 不用 | 理由 |
|---|---|---|---|
| Office 密级标签 | 标准属性 `MSIP_Label_<GUID>_Name`,`zipfile` + XML 读 | 扫页眉页脚文本作为主手段 | 属性是标准字段,不用猜模板;文本匹配退为无标签文件的兜底 |
| docx / pptx / xlsx 取文本 | `python-docx` (MIT, 2 依赖)、`python-pptx` (MIT, 4)、`openpyxl` (MIT, 1) | `markitdown` (38 依赖) | 前者按需引入即可;后者为省几行代码拉进一大片依赖 |
| PDF 取文本 | `pdfminer.six` (3 依赖) | Apache Tika | Tika 要 JVM 与常驻服务 |
| 手机号识别 | `phonenumbers` (Google libphonenumber 移植, 0 依赖) | 自写正则 | 带号码规划校验,误报远低于正则 |
| IMEI / IMSI / 证件号 | 自己实现三个校验:IMEI 的 Luhn 校验位、IMSI 的 MCC/MNC 与长度结构、居民身份证的 GB 11643 校验位(约 40 行) | `python-stdnum`(LGPL) | 只需要这三种,不值得为此引入 copyleft 依赖。关键是用**校验位**而不是形状匹配——正则在满是编号的语料里误报高 |
| 自由文本个人信息(姓名、地址) | 不做 | `presidio-analyzer`(31 依赖,拉 spaCy / transformers / stanza) | 依赖重,且 NER 会带来这一维最不能承受的误报;自由文本已列入边界 |
| 判断文件真实类型 | `python-magic` (MIT, 0 依赖) | 只看扩展名 | 扩展名可以改 |
| 策略外置 | 带版本的规则文件 + 哈希(与安全维同机制) | OPA / Rego | 判定标准主要是判定器提示与小表格,引入策略引擎与 DSL 不划算 |

必须自己写的部分:`content_id` 规范化指纹、数据载荷的形状判定(多行同构、字段数一致、行数与体积阈值)、白名单机制、`data_source` 的对照提示词。这些没有现成实现,而且都是本领域特有的。

许可已逐个核实:`phonenumbers` Apache-2.0(仓库 LICENSE),`pdfminer.six`、`python-docx`、`python-pptx`、`openpyxl`、`python-magic` 均为 MIT,都允许商用。唯一的 copyleft 备选 `python-stdnum`(LGPL)已改为自己实现,避免这项讨论。

自写的三个校验也要有测试:每个校验器给正例、改一位的反例、以及形状相同但校验位不对的反例。

## 角色与身份:现状与要补的

现状(核过代码):

| | 现状 |
|---|---|
| 角色系统 | 没有,只有 EID 字符串比较 |
| 管理员判定 | config 里 `audit_admin_eid="ADMINMM"` 用于 1 处;`market.py` 里另有 4 处硬编码 `"ADMINMM"` 字面量 |
| 身份来源 | `X-User-EID` 请求头,服务端只做大写归一,不校验 |
| 前端登录 | 输入 EID 存 localStorage,`isAdmin = eid === 'ADMINMM'`,无密码、无 SSO |
| `ezhgmio` | 只作为 `audit_mr_reviewer`(可疑上传的 GitLab 评审人),不是管理员 |

要补三件:

1. **管理员改成配置名单** `audit_admin_eids`,`market.py` 那 4 处字面量换成同一个判断,并把 `ezhgmio` 加进名单。现在改管理员要改代码。
2. **白名单写入端点用共享密钥保护** `X-Admin-Token`,与已有的 `AUDIT_WEBHOOK_TOKEN` 同一模式。SSO 之前,密钥能证明"确实是管理员做的",EID 头只表示"声称是谁";两者都记录。
3. **不做 RBAC 框架。** 两种能力(看全部、维护白名单)用一个 `is_admin(eid)` 加一个密钥就够。身份不可验证时,权限模型不构成控制,所以角色分层等 SSO。

## 要甲方的两件事,都不阻塞开发

| | 内容 | 没有答案时的默认 |
|---|---|---|
| 报备 | very-high confidential 我们硬拒(决策第 7 条) | 按硬拒实现,文档写明差异 |
| 上生产前确认 | DICIRA 引用的填写规范(编号格式还是链接);内部是否已有可接入的客户/伙伴名单 | 引用按自由文本 + URL 校验;名单不接 |

## 怎么实现

**检查项**(沿用现有报告契约 `{state, reference, checks[]}`,新增一组):

| id | 标签 | 查什么 | 谁来查 |
|---|---|---|---|
| `data_classification` | 密级标记 | Office 文件内嵌的密级标签属性;无标签时看正文与附件文本里的级别字样 | 确定性(属性 + 词表) |
| `data_payload` | 夹带数据 | 附件是文档或数据集;正文里出现成批记录 | 确定性(形状与规模) |
| `personal_data` | 个人数据超范围 | 有固定格式的个人标识符(IMSI/IMEI/MSISDN、PLMN、私人邮箱、证件号) | 确定性(格式) |
| `data_source` | 数据来源 | 指令要求读取或发送什么,与声明的输入是否一致 | 语义层(复用安全维的判定器) |

**载荷判定看形状与规模,不看单个数字。** 判据:附件扩展名属于文档或数据集类;同一形状的记录成批重复(多行同构、字段数一致);表格行数与体积超过阈值。几行合成示例不触发,验收里有对应用例。

**内容指纹要落库。** 现有的 `_content_key` 只是 600 秒内存缓存的键,含 skill 名字与 zip 原始字节,不持久化,重新打包就变,不能当审批的键。新增规范化的 `content_id`,写进审计记录,拒绝时返回给作者。

**状态模型**:两个独立判定,仍然只有一个可见性闸门 `rp_ai_skill.status`,由投影重算,写入者只有对帐器:

- 安全判定 = 通过 且 数据判定 = 通过(含白名单放行) → approved
- 安全判定 = 可疑 → pending,等复核 MR(数据维度不产生 pending)
- 安全判定 = 危险 或 数据判定 = 拒绝 → 不入库,只留审计记录

**附件要能读文档**:目前只把 `.md .txt .json .yaml .yml .toml .ini .cfg .rst .csv .properties` 当文本,docx / pptx / xlsx / pdf 读不了,而密级标记和夹带的数据主要在这些文件里。要加文本抽取;抽不出来(加密、损坏、格式不支持)计一条"未能核实"命中。

**前端**:报告页新增"数据合规"一节,与安全一节同一种呈现(通过的检查项也列出,命中项展开是四要素);拒绝页给出参考编号、内容指纹与命中清单,并说明申请审批的路径;输入契约与 name/description 同屏填写,不单开一屏问卷;管理员另有一个白名单维护页(列表、新增、作废、导出)。EDS 组件,不写死颜色。

## 怎么验收

| 测什么 | 通过标准 |
|---|---|
| 密级标记分级 | 构造四级标记的文档各若干份(一组用内嵌标签属性,一组只有页眉页脚文本):very-high 与 confidential 一律拒绝(只能由白名单放行),internal 与 public 全部通过 |
| 密级标记误报 | 在公开语料(408 个真实市场 skill)与库内现有 skill 上,密级标记命中数为 **0** |
| 数据载荷命中 | 附带真实形状的数据集(千行 csv、日志文件、xlsx 表)必须命中 |
| 数据载荷不误报 | 5–20 行合成示例、配置文件、代码脚本不得命中;库内现有 skill 的载荷命中为 **0** |
| 个人标识符命中 | 合成样本(IMSI/IMEI/MSISDN/PLMN/私人邮箱/证件号)全部命中,IMEI 与证件号须通过校验位验证而非仅形状匹配 |
| 个人标识符误报 | 库内现有 skill(其中 16 个是 Radio 研发测试类,含频率、DUT 编号、站点编号等形状相近的数字)误报为 **0**,这是最容易出错的一项 |
| 数据来源命中 | 指令写"读取客户日志目录并总结"、"连到生产网元导出参数"必须命中;声明"只读使用者粘贴的文本"却要求读 `~/customer_logs` 必须命中,证据含两边原文 |
| 数据来源不误报 | 指令只读使用者提供的文本、仓库内文件或公开资料的 skill 不得命中;库内现有 skill 的来源类命中需人工逐条确认 |
| 文档抽取 | docx / pptx / xlsx / pdf 各一份带标记文件都能读到标记;加密或损坏文件计一条"未能核实"命中 |
| 拒绝不留痕迹 | 命中且不在白名单 → 库里查不到任何 skill 记录(只留审计事件);返回内容含参考编号、内容指纹、命中清单 |
| 内容指纹稳定 | 同一内容重新打包(zip 时间戳、成员顺序、压缩级别不同)或改 skill 名字后,`content_id` 不变;正文或成员内容任何改动则必变 |
| 白名单放行 | 加白名单后重新上传同一内容 → 上架,审计事件记"经白名单 `<id>` 放行";过期或作废的条目不放行 |
| 判定波动下审批不失效 | 同一内容连续上传多次,命中清单不同也仍匹配同一条白名单 |
| 白名单写入受保护 | 没有 `X-Admin-Token` 的写入请求返回 403;仅凭 `X-User-EID: ADMINMM` 不能写入 |
| 抽查清单 | 能导出全部白名单条目及使用记录,含审批人、审批引用、创建与失效时间 |
| 审计可重放 | 对同一版本用同一 `policy_id` 重跑,命中项与首次一致 |
| 回扫 | 库内全部 skill 出报告,人工核对命中项 |

## 边界

- **归属检不出来。** 平台约束的是有没有夹带数据、指令要读什么,不是数据属于谁。
- **正文里散写的信息检不全。** 只覆盖有校验位或固定结构的标识符和成批记录;散文里提到的家庭情况、健康信息不会被发现,做这类识别要引入 NER,误报代价超过收益。
- **审批引用的真伪不验证。** 平台记录编号与审批人,真伪由 DICIRA 流程负责。
- **EID 不可信,直到有 SSO。** 白名单写入靠密钥保护,`X-User-EID` 只表示"声称是谁"。
- **白名单按内容放行。** 重新上传时新增的命中会被一并放行。
- **只覆盖"指令写了什么",不覆盖"实际发生了什么"。** 使用者在会话里粘贴的数据不在本维度。
- **来源判定依赖语义层,会判错。** 误判会拒掉一次正常上传,需要一次管理员往返。
- **规则到期即降级。** 9 月后若无新规定,不再自动通过。
