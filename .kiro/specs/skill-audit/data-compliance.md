# Skill 审计 · 数据合规维度

> 状态:**设计稿,尚未实现**。安全合规维度(`security-compliance.md`)已实现并有实测数据;这一维只有设计与验收标准。
> 依据:RTE LT 2026-06-02 批准的临时数据决定(有效期至 2026 年 9 月)。

上传的 skill 除了"会不会害人"(安全维度),还要判"这份内容允不允许放进云"。不涉及技术的同事读到"我们已经定下来的"为止即可,后面是工程细节。

## 甲方的规定

RTE/RCE 自有或共享的数据,配合 Amazon Q / Kiro 使用**不需要审批**,但三类例外:

| # | 例外 | 说明 |
|---|---|---|
| 1 | 客户与伙伴拥有的数据 | 归属不在我们这边的数据 |
| 2 | 按 ISRA 分类为 **very-high confidential** 的数据 | 公司分类体系的最高一级 |
| 3 | 超出基本商务信息的个人数据 | 允许的只有:姓名、signum、公司邮箱与电话、职位、组织 |

这三类要走 *Data in Cloud Infrastructure Risk Assessment Instruction*,由 **L3 manager 逐案决定**;L3 有权按需另开例外。

两点容易读错:

- **Internal 不是例外。** 公司分类有四级(Public / Internal / Confidential / Very High Confidential),规定点的是最高一级。规定所在的那份材料自己页脚就写着 *Ericsson Internal*。
- **规定管的是"使用",不是"发布"。** 它约束把数据交给 Kiro 处理;没有专门谈把数据放进一个共享的 skill 仓库。这个差别决定了下面第 6 条的取舍。

配套的方向性材料(Scalable AI — Way forward, 2026-06-05)写明:**逐案治理不可扩展**。所以这一维要做的不是"再加几条红线",而是把这套判断变成上传流程里可自动执行、可留痕的一步。

## 这道检查会做什么

和安全维度一样,结论只有三种,并且每条命中都给出位置、原文、含义和怎么改。

| 结果 | 什么情况 | 处理 | 上传者看到 |
|---|---|---|---|
| **通过** | 没有命中,且声明为公司自有 | 直接上架 | "数据合规检查通过" |
| **需审批** | 命中三类例外之一,或声明与检测结果矛盾 | 不公开,要求补审批凭据(DICIRA 评估编号或链接 + 审批人 signum);凭据齐全后上架,详情页标注依据 | 命中项 + "请脱敏,或补上审批凭据" |
| **拒绝** | 材料带 very-high confidential 密级标记 | 不入库 | 拒绝原因 + 参考编号 + 说明该走审批使用、而非发布 |

举一个命中的样子:

```
数据合规 · 个人数据超出允许范围      需审批
  位置    logs/drive-test.csv:142
  原文    ...,460019876543210,86138****1234,...
  含义    行首字段是 IMSI(移动用户识别码),随后是手机号;两者都属于超出
          "姓名/signum/公司邮箱与电话/职位/组织"范围的个人数据
  怎么改  用占位符替换真实标识符,或改用合成数据;确需保留则补审批凭据
  依据    RTE LT 2026-06-02 临时数据决定(至 2026-09)
```

## 为什么单独成一维,而不是给安全维度加红线

现有六个检查项(密钥、危险指令、隐藏指令、提示注入、附件安全、其他)问的都是"这个 skill 会不会害人"。数据合规问的是另一件事,四个方面不同:

| | 安全维度 | 数据合规 |
|---|---|---|
| 谁决定 | 安全评审人 | **上传者所在组织的 L3 manager** |
| 记录在哪 | 我们的复核 MR | ISRA / DICIRA 风险评估 |
| 怎么改 | 删掉恶意内容 | **脱敏,或补审批凭据**——内容本身可能完全正当 |
| 规则寿命 | 稳定 | **临时指令,9 月到期**,要能独立替换 |

误报代价也不同:客户名、站点名往往就是普通词,把这类命中做成硬拒会挡住正常上传。所以这一维的默认动作是转审批,不是拒绝。

代码现状:`app/services/skill_audit/` 与 `skill_audit/rules.md` 目前**没有任何**密级、个人数据或客户数据相关逻辑,`secret` 只管凭据(API key、密码、私钥)。这一维是纯新增,不改动现有判定。

## 能自动检出什么,检不出什么

| 规定的例外 | 可用信号 | 精确率 |
|---|---|---|
| very-high confidential | 文档密级标记(页眉页脚、文档属性里的固定字样) | **高**——打标记是规定动作,由材料所有者自己标 |
| 个人数据超范围 | IMSI / IMEI / MSISDN、私人邮箱域、证件号等有固定格式的标识符 | 中——格式化标识符高,自由文本里的个人信息低 |
| 客户与伙伴数据 | 客户名清单、网元名、小区名 | **低**——见下 |

检不出来的是**归属**。一份 RAN 配置,是实验室造的还是从客户网上导出的,内容上无法区分。所以纯检测这条路走不通,设计必须建立在三件事的组合上:

1. **上传者声明**(归属只有上传者知道)
2. **可自动检出的信号**(密级标记、格式化标识符)
3. **两者交叉核对**(声明"无客户数据"却扫到运营商网络标识符,就把矛盾摆出来)

第 3 条是这套设计的核心:它把"无法检测归属"变成"可以核对矛盾"。

## 我们已经定下来的

以下七条不去问甲方,理由写在每条后面。

**1. 平台不做审批路由,只要求审批凭据。**
L3 manager 是上传者自己组织里的人,平台猜不了也不该猜。触发例外时必须填 DICIRA 评估引用 + 审批人 signum,平台校验非空与格式、不可修改地记入审计事件、在报告和详情页显示。平台**不验证凭据真伪**(无法验证外部编号),但记录可追溯到人和时间。数据分类与风险决策的责任在数据所有者,平台负责校验与留痕。

**2. 客户名单第一版不做。**
只做高精度结构化标识符:IMSI / IMEI / MSISDN、PLMN(MCC-MNC)、私人邮箱域、证件号格式。不做客户名、网元名、小区名——库里 20 个 skill 里 16 个是 Radio 产品研发测试类,这些词天天出现,做了就是持续误报,而持续误报会让人学会忽略告警。名单以后到手,加一个规则文件即可。

**3. 密级标记用封闭级别词表,不猜模板。**
匹配四级级别词的大小写与连字符变体,规则放在可改的文件里。匹配到标记但级别读不出 → 转审批。

**4. 只管上传入库,不管运行时。**
用户在会话里粘贴客户日志属于另一个控制点(网关侧),skill 市场看不见。控制点要放在能观测的位置。

**5. 库里现有的 skill 全部回扫,只出报告,不自动下架。**
对既有数据套新规则,先测量再决定处置,避免用启发式规则破坏在用目录。

**6. 带 very-high confidential 标记的材料直接拒绝入库,并在拒绝文案里指向审批流程。**
这一条**比规定更严**,理由:规定约束的是"使用数据",而 skill 仓是共享持久存储,任何人的 agent 都会读到,发布等于再分发。按数据最小化与需知原则,共享目录不应承载最高密级材料;审批路径是为了在会话中使用这类数据,不是为了把它发布到市场。这个差异需要**向甲方报备**(见下一节),不作为提问。

**7. 策略带版本与生效期。**
规则文件里写 `policy_id: RTE-LT-2026-06-02` 与 `effective_until: 2026-09-30`;审计记录存策略 id 与哈希(与现有 `rules_hash` 同机制);报告显示判定依据;过期后启动即告警,并且判定从"自动通过"降为"需审批",不会悄悄失效。

## 要甲方的两件事,都不阻塞开发

| | 内容 | 没有答案时的默认 |
|---|---|---|
| 报备 | very-high confidential 我们硬拒(上面第 6 条) | 按硬拒实现,文档写明差异 |
| 上生产前确认 | DICIRA 引用的填写规范(编号格式还是链接);内部是否已有可接入的客户/伙伴名单 | 引用按自由文本 + URL 校验;名单不接 |

## 怎么实现

**检查项**(沿用现有报告契约 `{state, reference, checks[]}`,新增一组):

| id | 标签 | 查什么 |
|---|---|---|
| `data_classification` | 密级标记 | 正文与附件文本里的公司密级标记及其级别 |
| `personal_data` | 个人数据超范围 | 有固定格式的个人标识符(IMSI/IMEI/MSISDN、私人邮箱、证件号) |
| `declaration_conflict` | 声明与内容不一致 | 声明为"无"但检测到对应信号 |

**上传表单新增声明**(必答、无默认值,事后修改视为新版本并重新判定):是否含客户/伙伴数据;ISRA 密级(四级下拉);是否含超出基本商务信息的个人数据。触发例外时追加:DICIRA 引用 + 审批人 signum。

**状态模型**:两个独立判定,仍然只有一个可见性闸门。`rp_ai_skill.status` 继续是唯一闸门,由投影重算,写入者仍只有对帐器:

- 安全判定 = 通过 且 数据判定 = 通过 → approved
- 任一维未结清(安全待复核 / 数据待凭据) → pending
- 安全判定 = 危险 或 数据判定 = 拒绝 → 不入库

**附件要能读文档**:目前只把 `.md .txt .json .yaml .yml .toml .ini .cfg .rst .csv .properties` 当文本,**docx / pptx / xlsx / pdf 读不了**,而密级标记和客户数据主要就在这些文件里。要加文本抽取;抽不出来(加密、损坏、格式不支持)按"未能核实"转审批,不放过。

**前端**:上传向导第一屏加声明表单,报告页新增"数据合规"一节,与安全一节同一种呈现方式(通过的检查项也列出、命中项展开是四要素)。EDS 组件,不写死颜色。

## 怎么验收

实现后按下面几条测,数字都要可复现:

| 测什么 | 通过标准 |
|---|---|
| 密级标记分级 | 构造四级标记的文档各若干份:very-high 全部拒绝,confidential 全部转审批,internal 与 public 全部通过 |
| 密级标记误报 | 在公开语料(408 个真实市场 skill)与库内现有 skill 上,密级标记命中数为 **0**(它们不含公司密级标记) |
| 个人数据标识符 | 合成样本(IMSI/IMEI/MSISDN/PLMN/私人邮箱/证件号)全部命中 |
| 个人数据误报 | 库内现有 skill(其中 16 个是 Radio 研发测试类,含频率、DUT 编号、站点编号等形状相近的数字)误报为 **0** —— 这是这一维最容易出错的地方 |
| 交叉核对 | 声明"无"且植入标识符的样本,必须转审批 |
| 文档抽取 | docx / pptx / xlsx / pdf 各一份带标记文件都能读到标记;加密或损坏文件转审批 |
| 回扫 | 库内全部 skill 出报告,人工核对命中项 |

## 边界

- **归属检测不了。** 客户数据是否真属于客户,只能靠声明;平台能做的是核对矛盾与留痕。
- **自由文本里的个人信息检不全。** 只覆盖有固定格式的标识符,散文里的家庭情况、健康信息这类不会被发现。
- **凭据真伪不验证。** 平台只校验存在与格式,记录可追溯,真伪由审批流程负责。
- **不管运行时。** 会话里粘贴的数据不在这一维范围内。
- **规则到期即降级。** 9 月后若无新规定,判定不再自动通过,统一转审批。
