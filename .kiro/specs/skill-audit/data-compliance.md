# Skill 审计 · 数据合规维度

> 状态:**设计稿,尚未实现**。安全合规维度(`security-compliance.md`)已实现并有实测数据;这一维只有设计与验收标准。
> 依据:RTE LT 2026-06-02 批准的临时数据决定(有效期至 2026 年 9 月)。

上传的 skill 除了"会不会害人"(安全维度),还要判"这份内容允不允许放进云"。不涉及技术的同事读到"我们已经定下来的"为止即可,后面是工程细节。

## 甲方的规定

RTE/RCE 自有或共享的数据,配合 Amazon Q / Kiro 使用**不需要审批**,但三类例外:

| # | 例外 | 说明 |
|---|---|---|
| 1 | 客户与伙伴拥有的数据 | 归属不在我们这边的数据 |
| 2 | 按 ISRA 分类为 **very-high confidential** 的数据 | 公司分类体系的最高一级 |
| 3 | 超出基本商务信息的个人数据 | 允许的只有:姓名、signum、公司邮箱与电话、职位、组织 |

这三类要走 *Data in Cloud Infrastructure Risk Assessment Instruction*,由 **L3 manager 逐案决定**;L3 有权按需另开例外。

两点容易读错:

- **Internal 不是例外。** 公司分类有四级(Public / Internal / Confidential / Very High Confidential),规定点的是最高一级。规定所在的那份材料自己页脚就写着 *Ericsson Internal*。
- **规定管的是"使用",不是"发布"。** 它约束把数据交给 Kiro 处理;没有专门谈把数据放进一个共享的 skill 仓库。这个差别决定了后面第 7 条的取舍。

配套的方向性材料(Scalable AI — Way forward, 2026-06-05)写明:**逐案治理不可扩展**。所以这一维要做的不是"再加几条红线",而是把这套判断变成上传流程里可自动执行、可留痕的一步。

## 这道检查会做什么

出发点是一句话:**skill 是"怎么做一件事"的指令,不是数据。** 它需要指令、代码和合成示例;它不需要真实日志、导出表、客户文档或数据集。所以这一维查的不是"这份数据属于谁",而是"这个上传里有没有不该带的东西"。

和安全维度一样,结论只有三种,每条命中都给出位置、原文、含义和怎么改。

| 结果 | 什么情况 | 处理 | 上传者看到 |
|---|---|---|---|
| **通过** | 没有命中 | 直接上架 | "数据合规检查通过" |
| **需处理** | 命中密级标记(非最高级)、数据载荷或个人标识符 | 不公开。两种方式清掉:**删除或改成合成示例**(常见),或**补审批凭据**(DICIRA 评估编号/链接 + 审批人 signum) | 命中项 + 两种做法 |
| **拒绝** | 材料带 very-high confidential 密级标记 | 不入库 | 拒绝原因 + 参考编号 + 说明该走审批使用、而非发布 |

举一个命中的样子:

```
数据合规 · 个人数据超出允许范围      需处理
  位置    logs/drive-test.csv:142
  原文    ...,460019876543210,86138****1234,...
  含义    行首字段是 IMSI(移动用户识别码),随后是手机号;两者都属于超出
          "姓名/signum/公司邮箱与电话/职位/组织"范围的个人数据
  怎么改  删掉这个文件,或用占位符/合成数据替换真实标识符;确需保留真实数据
          则补审批凭据
  依据    RTE LT 2026-06-02 临时数据决定(至 2026-09)
```

## 为什么单独成一维,而不是给安全维度加红线

现有六个检查项(密钥、危险指令、隐藏指令、提示注入、附件安全、其他)问的都是"这个 skill 会不会害人"。数据合规问的是另一件事,四个方面不同:

| | 安全维度 | 数据合规 |
|---|---|---|
| 谁决定 | 安全评审人 | **上传者所在组织的 L3 manager** |
| 记录在哪 | 我们的复核 MR | ISRA / DICIRA 风险评估 |
| 怎么改 | 删掉恶意内容 | **删除或脱敏,或补审批凭据**——内容本身可能完全正当 |
| 规则寿命 | 稳定 | **临时指令,9 月到期**,要能独立替换 |

误报代价也不同:客户名、站点名往往就是普通词,把这类命中做成硬拒会挡住正常上传。所以这一维除了最高密级标记以外,默认动作是转处理,不是拒绝。

代码现状:`app/services/skill_audit/` 与 `skill_audit/rules.md` 目前**没有任何**密级、个人数据或客户数据相关逻辑,`secret` 只管凭据(API key、密码、私钥)。这一维是纯新增,不改动现有判定。

## 核心取舍:不问归属,禁止载荷

三类例外里,只有一部分能被自动看见:

| 规定的例外 | 可用信号 | 精确率 |
|---|---|---|
| very-high confidential | 文档密级标记(页眉页脚、文档属性里的固定字样) | **高**——打标记是规定动作,由材料所有者自己标 |
| 个人数据超范围 | IMSI / IMEI / MSISDN、私人邮箱域、证件号等有固定格式的标识符 | 中——格式化标识符高,自由文本里的个人信息低 |
| 客户与伙伴数据 | 客户名清单、网元名、小区名 | **低**——普通词太多,误报会淹掉真信号 |

**检不出来的是归属。** 一份 RAN 配置,是实验室造的还是从客户网上导出的,内容上无法区分。

第一版设计曾打算用"上传者声明 + 检测 + 交叉核对"补这个缺口:表单里填三项(是否含客户数据、ISRA 密级、是否含超范围个人数据),声明与检测矛盾就转审批。**这个设计被换掉了**,原因:勾选框不阻止任何事。把客户日志贴进正文、再在"是否含客户数据"选"否",系统照样放行——声明既没拦住数据,也没产生真实证据,只是转移了责任;而代价是每次上传都要填,而绝大多数上传不涉及这三类数据。

换成一个可验证的命题:**判"是不是数据",而不是判"是谁的数据"**。判归属不可能,判载荷可以:

| 检查 | 看什么 |
|---|---|
| 密级标记 | 正文与附件文本里的公司密级级别字样 |
| 数据载荷 | 附件是文档或数据集(docx/pptx/xlsx/pdf、大 csv、日志),或正文里出现成批记录 |
| 结构化标识符 | IMSI/IMEI/MSISDN、PLMN(MCC-MNC)、私人邮箱域、证件号格式 |

拿实际情形逐个试,这是判断两种设计强弱的依据:

| 情形 | 声明式 | 载荷式 |
|---|---|---|
| 客户网络配置贴进正文 | 勾"否"就过 | 结构化标识符 + 成批记录命中 |
| 附一份标着 Confidential 的客户 PPT | 勾"否"就过 | 密级标记命中,精确率高 |
| 附 5 行合成测试数据 | 要如实填,纯摩擦 | 不命中(载荷判定看形状与规模) |
| 指令写"去读客户服务器上的日志并总结" | 勾"否"也合理,上传本身不含数据 | **也检不出**——属于运行时控制点,见"边界" |

四种情形里载荷式在三种上更强,第四种两种设计都不行。它更可取不是因为更聪明,而是因为把不可验证的命题换成了可验证的命题,并且把摩擦挪到了少数真正需要判断的上传上。

## 我们已经定下来的

以下九条不去问甲方,理由写在每条后面。

**1. 表单只加一处确认,不加分类声明。**
最后一屏一个勾选:"确认此 skill 不含客户/伙伴数据、very-high confidential 材料或超范围个人数据",连同身份、时间、策略版本记录下来。它的作用是告知与留痕,**不假装是控制手段**——控制由检测承担。三项分类下拉不做,理由见上一节。

**2. 例外填报只在命中后出现。**
命中项旁边才要求 DICIRA 引用 + 审批人 signum。这时人是对着"logs/drive-test.csv:142 有 IMSI"做决定,而不是空泛表态,填出来的东西才有意义。

**3. 平台不做审批路由,只要求凭据。**
L3 manager 是上传者自己组织里的人,平台猜不了也不该猜。平台校验凭据非空与格式、不可修改地记入审计事件、在报告与详情页显示,但**不验证凭据真伪**(外部系统的编号无法核验)。数据分类与风险决策的责任在数据所有者,平台负责校验与留痕。

**4. 客户名单第一版不做。**
只做高精度信号:密级标记、数据载荷形状、结构化标识符。不做客户名、网元名、小区名——库里 20 个 skill 里 16 个是 Radio 产品研发测试类,这些词天天出现,做了就是持续误报,而持续误报会让人学会忽略告警。名单以后到手,加一个规则文件即可。

**5. 密级标记用封闭级别词表,不猜模板。**
匹配四级级别词的大小写与连字符变体,规则放在可改的文件里。匹配到标记但级别读不出 → 转处理。

**6. 只管上传入库,不管运行时。**
用户在会话里粘贴客户日志属于另一个控制点(网关侧),skill 市场看不见。控制点要放在能观测的位置。

**7. 带 very-high confidential 标记的材料直接拒绝入库,并在拒绝文案里指向审批流程。**
这一条**比规定更严**,理由:规定约束的是"使用数据",而 skill 仓是共享持久存储,任何人的 agent 都会读到,发布等于再分发。按数据最小化与需知原则,共享目录不应承载最高密级材料;审批路径是为了在会话中使用这类数据,不是为了把它发布到市场。这个差异需要**向甲方报备**(见下一节),不作为提问。

**8. 库里现有的 skill 全部回扫,只出报告,不自动下架。**
对既有数据套新规则,先测量再决定处置,避免用启发式规则破坏在用目录。

**9. 策略带版本与生效期。**
规则文件里写 `policy_id: RTE-LT-2026-06-02` 与 `effective_until: 2026-09-30`;审计记录存策略 id 与哈希(与现有 `rules_hash` 同机制);报告显示判定依据;过期后启动即告警,并且判定从"自动通过"降为"需处理",不会悄悄失效。

## 怎么审计

审计要回答的是"谁在什么依据下发布了受限内容",并且要能重放。可查的事实:

| 事实 | 存在哪 | 能否重算 |
|---|---|---|
| 命中项(位置、原文、类别、严重度) | 审计事件,追加写 | 能——策略 id 与规则哈希已钉住,对同一版本重跑得到同样结果 |
| 上传者身份与时间 | 审计事件 | 能 |
| 判定依据的策略版本 | `policy_id` + `effective_until` + 哈希 | 能 |
| 例外处置(删除 / 提供凭据 + 审批人) | 审计事件,追加写、不可修改 | 能 |
| 发布前的确认动作 | 审计事件(身份 + 时间 + 策略版本) | 能 |
| 当时内容长什么样 | skill 仓的 git 历史 | 能 |

审计**做不到**两件事,不能含糊:证明确认框勾得诚实;验证 DICIRA 编号真伪。

## 要甲方的两件事,都不阻塞开发

| | 内容 | 没有答案时的默认 |
|---|---|---|
| 报备 | very-high confidential 我们硬拒(上面第 7 条) | 按硬拒实现,文档写明差异 |
| 上生产前确认 | DICIRA 引用的填写规范(编号格式还是链接);内部是否已有可接入的客户/伙伴名单 | 引用按自由文本 + URL 校验;名单不接 |

## 怎么实现

**检查项**(沿用现有报告契约 `{state, reference, checks[]}`,新增一组):

| id | 标签 | 查什么 |
|---|---|---|
| `data_classification` | 密级标记 | 正文与附件文本里的公司密级标记及其级别 |
| `data_payload` | 夹带数据 | 附件是文档或数据集;正文里出现成批记录 |
| `personal_data` | 个人数据超范围 | 有固定格式的个人标识符(IMSI/IMEI/MSISDN、PLMN、私人邮箱、证件号) |

**载荷判定看形状与规模,不看单个数字。** 判据是:附件扩展名属于文档/数据集类;或同一形状的记录成批重复(多行同构、字段数一致);或表格行数与体积超过阈值。几行合成示例不触发——这是必须守住的行为,验收里有对应用例。

**状态模型**:两个独立判定,仍然只有一个可见性闸门。`rp_ai_skill.status` 继续是唯一闸门,由投影重算,写入者仍只有对帐器:

- 安全判定 = 通过 且 数据判定 = 通过 → approved
- 任一维未结清(安全待复核 / 数据待处理) → pending
- 安全判定 = 危险 或 数据判定 = 拒绝 → 不入库

**附件要能读文档**:目前只把 `.md .txt .json .yaml .yml .toml .ini .cfg .rst .csv .properties` 当文本,**docx / pptx / xlsx / pdf 读不了**,而密级标记和夹带的数据主要就在这些文件里。要加文本抽取;抽不出来(加密、损坏、格式不支持)按"未能核实"转处理,不放过。

**前端**:上传向导最后一屏加确认勾选;报告页新增"数据合规"一节,与安全一节同一种呈现方式(通过的检查项也列出、命中项展开是四要素);命中项旁边才出现凭据填报。EDS 组件,不写死颜色。

## 怎么验收

实现后按下面几条测,数字都要可复现:

| 测什么 | 通过标准 |
|---|---|
| 密级标记分级 | 构造四级标记的文档各若干份:very-high 全部拒绝,confidential 全部转处理,internal 与 public 全部通过 |
| 密级标记误报 | 在公开语料(408 个真实市场 skill)与库内现有 skill 上,密级标记命中数为 **0**(它们不含公司密级标记) |
| 数据载荷命中 | 附带真实形状的数据集(千行 csv、日志文件、xlsx 表)必须命中 |
| 数据载荷不误报 | 5–20 行合成示例、配置文件、代码脚本**不得**命中;库内现有 skill 的载荷命中为 **0** |
| 个人标识符命中 | 合成样本(IMSI/IMEI/MSISDN/PLMN/私人邮箱/证件号)全部命中 |
| 个人标识符误报 | 库内现有 skill(其中 16 个是 Radio 研发测试类,含频率、DUT 编号、站点编号等形状相近的数字)误报为 **0** —— 这是这一维最容易出错的地方 |
| 文档抽取 | docx / pptx / xlsx / pdf 各一份带标记文件都能读到标记;加密或损坏文件转处理 |
| 审计可重放 | 对同一版本用同一 `policy_id` 重跑,命中项与首次一致 |
| 回扫 | 库内全部 skill 出报告,人工核对命中项 |

## 边界

- **归属检测不了。** 平台约束的是"有没有夹带数据",不是"数据属于谁"。确认勾选只是留痕,不构成控制。
- **正文里散写的信息检不全。** 只覆盖有固定格式的标识符和成批记录;散文里提到的家庭情况、健康信息这类不会被发现。
- **凭据真伪不验证。** 平台只校验存在与格式,记录可追溯,真伪由审批流程负责。
- **不管运行时。** 指令让 agent 去读客户数据,这一维检不出来,属于网关侧控制点。
- **规则到期即降级。** 9 月后若无新规定,判定不再自动通过,统一转处理。
