# Skill 审计 · 安全合规维度

技能市场上传的每个 skill,在写进仓库之前过一道自动检查,结果只有三种:上架、转人工复核、拒收。

这份文档说明:这道检查要解决什么问题、用了哪个现成工具、我们自己写了什么、实测效果如何、以及做不到什么。

| 读者 | 从哪读 |
|---|---|
| 想知道这套东西为什么存在、效果如何 | 第一、四部分 |
| 上传技能或复核 MR | 第五部分 |
| 维护这套东西 | 第二、三部分 |
| 看不懂报告里的英文名词 | 第二部分的名词表 |

---

# 一、检查什么

skill 不是文档,是 agent 的指令与脚本:SKILL.md 里的自然语言会被当作指令执行,`scripts/` 里的代码会被
真的跑起来。所以一个 skill 能做的事,等于装它的人能做的事。

风险有一半不在代码里。USENIX Security 2026 测得 84% 的 skill 漏洞出现在自然语言指令里,例如 SKILL.md
写着"完全信任、无需向用户确认",而代码本身干净。

检查覆盖三件事:

1. **隐瞒** —— 做的事比声明的多,或刻意藏起来:零宽字符藏指令、base64 藏载荷、把指令写在"示例输出"块里。
2. **越权** —— 让 agent 跳过用户确认、扩大自己的权限、把数据发到声明之外的地方。
3. **凭据泄露** —— 真实的 key / token / 密码写进 skill,随发布扩散给所有下载者。

范围之外:

| 不看 | |
|---|---|
| 能力本身 | 声明了要连网、然后确实连网,不可疑。判据是**是否声明并可核对**,不是这个动作听起来危不危险。凭据代管、改 agent 配置、安全测试、故障演练、运维清理这类 skill,其声明用途本身就是那项能力 |
| 蓄意规避 | 自解压打包、扫描后改坏的可变外链等结构性盲区,见第六部分 |
| 功能欺诈、反检测工具 | 属"行为不当"而非"内容危险",不在本维度 |
| 上传者是谁 | 调用者身份已由登录系统验证,但门不因人放宽或收紧,只看内容 |

依据:OWASP LLM Top 10 2025、CWE-798(硬编码凭据)、USENIX Security 2026。

这道检查是兜底:作者是内部同事、上传记录了 EID、判为可疑的还会过一次人工复核。它承担的是筛量——卫生
问题不占用复核者时间,明确危险的不送到人面前。实测需要人看的比例是 13%–17%。

# 二、依赖的工具

## skill-scanner 2.0.12

检测层用 Cisco 开源的 `skill-scanner`,装在镜像里,专做 AI skill / MCP 安全审计。它提供:

| | 规模 |
|---|---|
| 检测规则 | 22 个类别、约 400 条规则,分 `core` / `atr` / `promptguard` 三个包 |
| 分析器 | static、YARA、pipeline(污点)、bytecode、behavioral、llm(语义)、meta(仲裁) |
| 策略预设 | `strict` / `balanced` / `permissive`,每档给出阈值、白名单、误报抑制 |
| 审计 SOP | 威胁分析提示词(300 行)、代码与声明一致性提示词(976 行)、误报过滤提示词(286 行)、注入防护定界规则 |
| 分类学 | 每条命中挂到公开分类学 AITech(9 个代码)上,分类依据可追溯 |

其中"代码与声明是否一致"就是第一部分要的隐瞒判据。

## 我们负责什么

| | 归谁 |
|---|---|
| 规则目录、类别、严重度、阈值、良性白名单、误报抑制、置信度 | 扫描器(改它的策略数据,不写 Python) |
| 审计用的提示词、输出 schema、注入防护 | 扫描器 |
| 什么时候扫、扫哪个目录、超时多久、失败怎么办 | 我们 |
| 把命中翻译成市场决定(上架 / 复核 / 拒收) | 我们,这是唯一一张需要维护的表 |
| 写入门、复核工作流、事实记录、报告呈现 | 我们 |
| 语义与仲裁用的模型 | kiro,经一个适配器挂在扫描器背后 |

**类别与严重度原样透传,不改名、不归并。** 两个例子:把 `obfuscation` 归成红线类"隐藏指令",`.py` 里的
中文注释就会被判危险;把 `TOOL_ABUSE_UNDECLARED_NETWORK`(未声明的网络访问)压成"未分类",就丢掉了正好
对应越权的判据。界面上的中文名称只是一张展示映射,没有映射的类别直接显示扫描器自己的 `title`。

# 三、怎么设计

## 代码在哪

审计能力已经拆到独立仓 **`rp-ai-miao/skill-audit`**(边界与契约见 [service-split.md](service-split.md))。
所以这张表分两半:

**在新仓 `skill-audit`**

| 文件 | 职责 |
|---|---|
| `skill_audit/scan.py` | 调 `skill-scanner`,原样读报告。没有报告 = 没查,不等于干净 |
| `skill_audit/verdict.py` | **裁决规则,唯一一张我们维护的表**。命中 → 上架 / 复核 / 拒收;另含"覆盖缺口归谁"的分类 |
| `skill_audit/pipeline.py` | 串起来:准备输入 → 前置检查 → 扫描 → 裁决;含进程内缓存 |
| `skill_audit/scanners.py` | 只剩凭据红线的前置正则检查 |
| `skill_audit/remediation.py` | 扫描器没给处置建议时补默认值(在结论装配处补,不在渲染处) |
| `skill_audit/skill_repo.py` | 按 commit sha 从 GitLab 读技能仓(重复性维度的语料) |
| `skill_audit/policy.yaml` | 扫描器的策略(阈值、预算、白名单),改这里而不是改 Python |
| `app/main.py` | 引擎的 HTTP 表面:`POST /v1/audits`(事件流)、`GET /v1/vocabulary`、`/health` |
| `app/judge.py` + `Dockerfile.judge` + `.kiro/agents/json-endpoint.json` | 判定器:HTTP 接口 → `kiro-cli acp`,以及只回 JSON、不带工具的 agent 定义 |

**留在门户**

| 文件 | 职责 |
|---|---|
| `app/services/audit_engine.py` | 调引擎的客户端 + DTO 镜像 + 去重键。门户对引擎的**唯一**接触面 |
| `app/services/audit_report.py` | 把命中翻成界面上的中文,未映射的类别照原样显示 |
| `app/services/skill_audit/gate.py` | 写入门与判定复用(`recent_audit`) |
| `app/services/skill_audit/reconcile.py` | 从 MR 状态重算 status |

## 一次扫描调用

审计 = `skill-scanner scan <目录>` 一次调用。检测、语义、仲裁都在它内部完成,我们只读报告:

| 分析器 | 看得到什么 |
|---|---|
| static + YARA | 固定模式:硬编码凭据、命令执行、下载即执行、不可见字符、同形字、编译产物 |
| pipeline | 命令链污点(网络输入流向执行) |
| bytecode | `.pyc` 完整性 |
| behavioral(给预算) | Python AST + 污点跟踪的多步行为 |
| llm | SKILL.md、配置与打包文本的意图,以及代码与声明是否一致 |
| meta | 二次过审:对着源码核实每条命中、合并同源、剔误报、排优先级;不找新威胁 |

检测各自独立,仲裁看全部——它要判断一条命中是不是误报,只能拿着命中回到源码里核实,所以必须看得到
其它层的结论。

**不能让 agent 自己去调扫描器。** 那需要 agent 持有执行权限,而它同时在读不可信内容;并且"确定性层跑过
没有"会取决于模型是否照做,而这必须是可验证的事实。

## 裁决结果是两件事,不是一件

审计产出两件**逻辑上独立**的事实,门的三种结果是它们的投影:

| | 回答什么 | 取值 |
|---|---|---|
| **覆盖度** `coverage` | 内容被检查了多少 | `complete` / `partial` / `none` |
| **判断** | 就检查到的部分,说明了什么 | 没问题 / 可疑 / 红线 |

投影成 `pass / suspect / danger` **对门本身是对的**——失败必须关闭。但下游有三个消费者,各要其中一维:

| 谁 | 他要问的 | 读哪一维 |
|---|---|---|
| 复核者 | 有没有人看过内容?要不要我自己逐行读 diff? | `coverage` |
| 作者 | 是我能修的,还是平台故障? | `cause` 推出的归属 |
| 运维 | 审计自身多久失败一次、失败在哪? | `cause` 计数 |

**所以这两维必须作为数据留下,不能只留一句话。** 曾经只留 `reason` 一句散文,后果是复核 MR 出现过只有表头
没有行的空表:复核者不知道为什么要看它,作者不知道改什么(同一个技能原样传了两遍),而"审计失败率"根本
无从统计。

这个分轴不是我们发明的。SARIF(OASIS 的静态分析结果交换格式,本扫描器也能输出)把"工具是否对每个目标跑完
每条规则"放在 invocation 层的 `executionSuccessful` 与 `toolExecutionNotifications`,把发现放在 results,
并且 `result.kind = review` 的定义就是"需要人来判断是否算问题"。同两维。**但不读它的 SARIF**:实测这个
扫描器只填 `executionSuccessful`、从不填 notifications,而加载失败时连 SARIF 都不输出——多写一份报告只换来
一个我们已经知道的布尔值。取它的词汇,值从我们已经在读的 JSON 报告里推。

### `cause`:为什么覆盖度不完整

闭集,只增不改。**每个取值必须同时给出归属与给复核者的一句话**,有测试强制;归属是 `cause` 的纯函数,
不单独存(两个能互相矛盾的字段就是两次出错的机会)。

| `cause` | 归属 | 什么情况 |
|---|---|---|
| `bundle_unloadable` | 作者 | 扫描器拒绝加载,内容一次都没被检查过。最常见是 frontmatter 没能解析成键值对 |
| `bundle_unreadable_member` | 作者 | 有个会运行的文件读不出来(`.pyz`、`.exe`、非 UTF-8 脚本),其余已检查 |
| `bundle_too_big` | 作者与平台 | 超出语义层预算,超出部分没被语义分析看过;确定性层仍扫了每个文件 |
| `scanner_timeout` | 平台 | 超时,不是查出了问题 |
| `scanner_broken` | 平台 | 无报告、无输出、报告不是有效 JSON、跑不起来 |
| `layer_failed` | 平台 | 语义或仲裁层自报失败 |

注意 `bundle_unreadable_member` 是 **`partial` 而不是 `none`**:我们看了,而且那条命中本身就是证据。
把它算成"什么都没看"会同时犯两个错——让复核者忽略已有判据,并把一次正常拦截计成平台故障。

**唯一的散文→结构转换点**是"没有报告时,这是包不可加载还是工具坏了",因为扫描器加载失败时不写任何报告,
只在 stderr 留一行。它匹配两个字符串(`Error loading skill`、`missing required field`),由
`tests/test_scanner_contract.py` 用**装着的那个扫描器**钉住,并有一条用真实出错内容跑扫描器的端到端测试。
措辞若变,测试先失败,不会静默把作者的笔误改判成我们的故障。

**历史记录只增不改**:老记录两列为 NULL,含义是"当时没记这一维",不从 `reason` 回填——那正是把事实换成
今天的判断。原始 `reason` 与扫描器的原始消息始终保留,所以将来要重新分类,是从事实重算。

## 判断:门槛与拒收

按顺序判断,先答覆盖度,再答判断:

1. `coverage != complete` → 复核。不区分是超时、崩了、还是包读不了。
2. 卫生类不参与门禁。缺 license、包里带压缩包、`__pycache__`、描述超长,只进报告。
3. 读不了的文件,只有在它是可执行文件时才拦,与严重度无关。读不了的数据文件(docx/xlsx/pdf/图片)不拦。
4. 严重度门槛是 high;`obfuscation` 与 `unicode_steganography` 在 medium 即拦——它们断言的是"刻意隐藏",
   按不变量属于隐瞒,而扫描器给这类的严重度通常只有 medium。
5. 没见过的类别按 medium 起拦。门槛是按严重度定的,而"刻意隐藏"那两类之所以 medium 就拦,靠的是我们知道
   它们的语义;新类别没有这个知识,把它读成"只是能力"是唯一会静默放过的方向。名单取扫描器两套词汇的并集
   (枚举 17 + 规则包 17,共 26),有测试从装着的扫描器读回来断言无遗漏。
6. 拒收要求确定性层与语义层对同一类别都给出 critical。只有一层命中的 critical 转复核。
7. 其余按最高严重度转复核。

**判断不单独存**:最高严重度与"两层是否一致"都能从已落库的 findings(带 `source`/`severity`/`category`)
现算。存它就是冗余,冗余就会不一致。

每个结论带一行 `reason`,进 `evaluate` 与 `upload` 的响应、进审计记录、也进复核 MR 正文。被拒时 422 的
detail 里也有它——否则作者只能原样重传。

语义层引用的片段要能在被审内容里找到;仲裁层的职责之一是拿命中回到文件里核实,核不实的剔为误报。

### 四条自洽性约束

1. **没见过的类别按 medium 起拦**(上面第 5 条),并有测试从装着的扫描器读回两套词汇断言名单无遗漏。
2. **`coverage != complete` = 转复核** —— "没查"和"查了没发现"是两件事。
3. **判定可复现** —— 记录存模型名 + 扫描器版本 + 策略文件自身的哈希。扫描器只在部分输出模式下附带自己的
   指纹,所以这个值由我们算:策略是决定判定的三个输入之一,说不出策略的记录事后无法解释。
4. **审计自身的健康要可观测** —— 前三条都把代价转给复核者,所以失败必须**可计数**。`coverage` 与 `cause`
   落库,`GET /api/audit/health?days=N` 给出窗口内的分布:`byState`、`byCoverage`、`byCause`,以及
   `platformFailures` / `platformFailureRate`(归属为平台的那些)与 `notExamined`(覆盖度为 `none` 的条数)。
   一次失败是个案,持续失败是我们的故障,而两者在单条记录上长得一样。

   两个刻意的选择:`notExamined` **只数 `none` 不数 `partial`**(部分覆盖里确实有东西被检查过,混在一起会
   夸大损失并掩盖复核者关心的区别);两列为 NULL 的老记录单独计入 `unclassified`,**不塞进任何桶**——那个数
   如果在涨,说明度量本身在退化。

## 策略配置

**用 `permissive` 作基线。** 官方选择树:不受信任/外部技能用 `strict`,普通 CI 用 `balanced`,受信任的
内部技能用 `permissive`。不用 `strict`——它的定位写明是 "untrusted / external skills and compliance
audits",代价实测过:一个真实中文技能在 strict 下 14 条命中、其中 12 条是 `HOMOGLYPH_ATTACK`——同形字攻击,
指用长得像 ASCII 的别国字符冒充,而这 12 条命中的是 `.py` 里正常的中文注释,balanced/permissive 下同一个包只有 1 条;而对恶意样本,三档抓到的完全一样。

要调轻重就 `severity_overrides`,要关噪声就 `disabled_rules`,`generate-policy` 可导出默认值。不在
Python 里重写一份:手写的名单会与工具的规则目录静默漂移。**自定义策略与默认值合并时,列表是替换而不是
追加**,覆盖任何白名单都必须整份重写。

**关噪声要按规则关,不能按类别整片关。** 扫描器有一个类别叫 `policy_violation`,装的是"规范问题"而不是
攻击行为:缺 license、包里夹带压缩包、描述超长、有文件读不出来。它在报告里条数最多,所以第一反应是把整个
类别加进 `disabled_rules`。但这个类别里有两条不能丢:

- `UNANALYZABLE_BINARY` —— 这是扫描器报告"这个文件我读不出来"的唯一方式。裁决规则第 3 条(读不了的可执行
  文件转复核)完全依赖它;关掉它,一个打包成 `.pyz`、谁也没读过的脚本会直接上架。
- `MANIFEST_DESCRIPTION_TOO_LONG` —— 描述超过 512 字符会让技能自身工作不正常(Agent Skills 的上限),
  作者必须知道。

所以做法是:类别保留,`disabled_rules` 只填具体规则 id;纯卫生的那几条进"永不参与门禁"的名单
(见裁决规则第 2 条),它们照常出现在报告里,只是不挡人。

**送给语义层的量绑在模型上,不绑在今天的语料上。** 默认值在 46 个真实技能上会截断 11%–21% 的文件,而被
截断的部分在报告里仍算"已审"。取值起点是上下文窗口,而不是当前语料的最大值——语料会长大:`claude-sonnet-5` 为 100 万 token,按语料约 3.5 字符/token 折算 ≈ 350 万字符,取三分之一留给 SOP、
已有 findings、输出与余量。

| 项 | 默认 | 取值 | 当前最大观测 |
|---|---|---|---|
| `max_total_prompt_chars` | 100,000 | 1,100,000 | 333,641(占 30%,还有 3 倍余量) |
| `max_instruction_body_chars` | 20,000 | 220,000 | 33,168 |
| `max_code_file_chars` | 15,000 | 330,000 | 89,682 |
| `max_referenced_file_chars` | 10,000 | 220,000 | 53,963 |

超出之后是分层退化,不是报错:扫描器截断并报 `LLM_CONTEXT_BUDGET_EXCEEDED`,裁决当"这一层未核实"→
转复核;确定性层不受预算约束,仍然扫了每个文件。这条只能是最后一道,不能是常态——代价落在作者身上,
而且他重传也没用。

`max_output_tokens` 不动:全量语料多轮下来共 269 次模型调用,最大回包 13,228 字符 ≈ 3,779 token,
默认 8192 从未成为约束。

**零宽字符阈值下调**:`permissive` 预设要 500 个(独立)或 100 个(有解码上下文)才触发,而真实隐写样本
只有 4–50 个。正常内容里零宽字符几乎不存在(OASB 85 个正常样本最大 0 个;内部语料 179 个可读文件里 1 个
文件含 1 个),所以取 3 / 2 仍有余量。

**扫描超时 900 秒**(中位 41、最大 91,超时记成"没查");`--use-behavioral` 默认关闭,理由见第六部分。

## 输入准备与凭据前置检查

**上传时就要拦下扫描器读不了的 frontmatter。** 我们自己的解析(`parse_frontmatter`)是刻意宽容的:YAML 解析
失败会回落到正则,好让一个稍有毛病的块仍能给出市场卡片上的名字。下游没有这份宽容——扫描器把它当 YAML 解,
解不出映射就**拒绝加载整个 skill**,于是审计变成"没有报告",门按"没查"转复核,复核者拿到一个没人看过的包。

所以 `_read_upload` 在审计之前多断言一条:frontmatter 块必须解析成 YAML 映射,且 `name`/`description` 非空;
不满足就 400,并**指名具体写法问题**。实测最常见的是**冒号后面少一个空格**——`name:foo` 在 YAML 里不是键值对
而是一整行字符串,于是字段"看着有、实际无"。生产上有个技能因此原样重传了两遍,因为它收到的回复从没说清哪里错。

**这道校验不能比扫描器更严。** 比工具更严会挡住它本会接受的技能,而作者无从知道是平台而不是扫描器把这次上传
拦下的——这与漏放同样糟。所以边界是**实测**出来的,不是照 `yaml.safe_load` 的对错来的:

| frontmatter | 扫描器 | 我们 |
|---|---|---|
| `name:foo`(冒号后无空格) | 拒绝加载 | 拦下,并指名少空格 |
| 制表符缩进、未闭合的流式集合 | 拒绝加载 | 拦下 |
| 缺 `name` 或 `description` | 拒绝加载 | 拦下 |
| 只有内联标签、没有 `---` 块 | 拒绝加载 | 拦下 |
| `description: A tool: does things`(值里裸冒号) | **能加载** | **放行** |
| `name:`(值为空) | **能加载** | **放行** |
| 带引号的值、值里有 URL | 能加载 | 放行 |

最后两行是第一版写错的地方:第一版用 `yaml.safe_load` 的失败当依据,于是拦下了扫描器接受的两种形状。
`tests/test_scanner_contract.py::test_the_upload_check_agrees_with_the_scanner` 用这 10 种形状**同时**断言
扫描器的行为与我们的判断,任一侧漂移都会失败。

输入准备在 `_materialize` 里做。**包内的压缩包要解开,并删掉原件**(递归,深度上限 3)。留在盘上它会被当成不透明二进制报成"读不了",
那是关于我们打包方式的发现而不是关于技能的;而且同一份字节会再送一遍给模型。量化见第四部分。

**密钥检出交给扫描器**(`hardcoded_secrets` 规则族 + promptguard 的 `secret_providers.yaml`)。但扫描器
自己读文件、自己调模型,提示词不经我们的手,写在 skill 里的真实凭据会被原样送进语义层。
所以保留一层**极小的正则红线前置检查**:目的不是覆盖面,而是在调用扫描器**之前**拦下明确的真实凭据
(命中即拒收),让它没有机会进入任何提示词。

## 模型与适配器

扫描器要一个 OpenAI 兼容端点,我们的模型是 kiro,所以中间有一个适配器。

**钉死 `claude-sonnet-5`,不用 `auto`**:门禁要对同一输入给出同一结论,并且判定要能归因到具体模型。
换模型不影响耗时,但影响判定——同一个包在不同模型下的命中数不同,所以校准必须在钉死的模型上做。

**模型名必须在启动时校验。** `kiro-cli chat --model <不存在的名字>` 会报错并列出可用模型,但
`kiro-cli acp --model <不存在的名字>` 静默接受,打错一个字就会静默用默认模型,归因不再成立。可用值:
`claude-opus-5`、`claude-sonnet-5`、`claude-sonnet-4.6/4.5/4`、`claude-opus-4.8/4.7/4.6/4.5`、
`claude-haiku-4.5` 等。

**拒收的第二个判据是另一类分析器,不是另一个模型。** 要抵抗同一模型的运行间波动,用扫描器自带的
`--llm-consensus-runs N`。

适配器把 `POST /v1/chat/completions` 翻成 ACP:起一个 `kiro-cli acp` 进程 → `initialize` /
`session/new` / `session/prompt` → 收集 `agent_message_chunk` → 按 Chat Completions 形状回包。

- **一次请求一个进程**:一次审计不该看到另一次审计的任何东西。
- **模型不持有任何工具**(`--trust-tools=`,并拒绝 `session/request_permission`)。只收文本、只回 JSON,
  注入没有可用的手段——它连文件系统都碰不到。
- **端点要鉴权**:它是网络上的模型入口。用扫描器本来就会发送的 `Authorization: Bearer <API key>` 校验,
  值与后端配置同源(同一个 env 文件),两边必然一致。未配置时不校验。
- **输出必须是 JSON**,三层保证:一个 `allowedTools: []` 且提示词要求"只输出一个 JSON 对象"的专用 agent;
  适配器从回包里提取 JSON(去代码围栏、按括号配平截取、丢弃尾随散文);仍非 JSON 时重试一次并重述要求,
  第二次仍失败则如实报错。交互式 agent 会把 JSON 请求答成 markdown 报告,而解析失败被报成
  `LLM_ANALYSIS_FAILED`,门据此判成"这一层没跑成"(46 个真实技能里曾有 10 个因此转复核)。
- 环境变量:`SKILL_SCANNER_LLM_PROVIDER=openai`、`SKILL_SCANNER_LLM_BASE_URL=<适配器>/v1`、
  `SKILL_SCANNER_LLM_API_KEY=<与适配器一致>`、`SKILL_SCANNER_LLM_MODEL=openai/claude-sonnet-5`。
  模型名要带 `openai/` 前缀,否则仲裁那条路会因 litellm 缺 provider 而失败,而主分析那条路不会——
  两条路的失败方式不同,只测一条会漏。

## 接进上传与编辑

- **判定是纯函数** `audit_skill(内容) → {状态, 命中详情}`:无副作用、幂等。
- **evaluate** 调它并返回结果,不入库;**publish** 内部再调一次做权威门禁(不信任前端的结果),再按状态
  分流:危险 → 422 不入库;通过 → 主分支;可疑 → 复核分支 + Draft MR。
- **门管的是"经门户写进仓库"这条路。** 仓库还有第二个入口:有人直接往技能仓推提交。
  `official_import.py` 把仓库里已有的技能导入数据库并标为 `approved`,不产生审计记录——那条路的安全性由
  技能仓自己的评审保证,不由这道门保证。
- **门挂在"把内容写进仓库"这个动作上,不挂在某条路由上。** 唯一写入口 `skill_storage.store()` 必须收到
  审计结论才肯写,并自己拒绝两件事:写入被判危险的内容;把待复核的内容写到主分支。新增写入路径时忘了
  审计是**签名错误**,不是安全事故。
- **编辑(`PUT /api/skills/{id}`)走同一道门**,分流规则与 publish 一致:危险 → 回滚这次编辑、只留审计
  记录、422;可疑 → 复核分支 + Draft MR 并把 status 退回 pending;通过 → 主分支。
- **跑不起来的审计不能改变已经发布的东西。** 失败关闭的代价可以落在提交者身上,前提是还没有东西上线。
  对已上架技能提交新版本时,若某个服务不通就什么都不改,返回 503 让人稍后重试。

## 判定复用

`evaluate` 与 `publish` 审同一批字节、相隔几秒,而一次审计要几十秒,所以复用结论。复用的键是内容哈希
(`content_sha`),有效期 600 秒。两级:先查进程内缓存(`pipeline._verdict_cache`),没有再查审计记录
(`gate.recent_audit`)。

- 记录这一级是必须的:API 多副本时两次调用可能落在不同进程,内存里的结论对另一个副本不存在,于是同一份
  内容被扫两遍——白付一次几十秒,而且两次可能给出不同结论。进程内缓存只是省一次数据库查询。
- 过期不复用:规则、扫描器或策略更新后立即生效。
- 记录是 finding 的持久形态,所以除类别与严重度外还存 `rule_id`、`aitech`、`remediation`。

## 复核工作流与状态

后端用有写权限的 GitLab token 把该版本提交到分支,开 Draft MR(怎么读写那个仓库见 [repo-access.md](repo-access.md)),标题带上传者(显示名 + EID),命中作为
评论贴上,指派评审人。合并 → 上线;关闭 → 拒绝。评论、审批、通知都用 GitLab 现成的。

派生字段必须能从事实重算出来:

- **事实**(不可变、只追加):审计事件与命中证据(`rp_ai_skill_audit_record` + `rp_ai_skill_finding`);
  复核决定由 GitLab 的 MR 状态承载;哪个版本在线由 git 仓库决定。
- **唯一的生命周期闸门**:`rp_ai_skill.status`(pending / approved / rejected)。
- **展示缓存**:`audit_state` 只说明"为什么还在 pending",不作闸门。
- **谁写 status**:发布与编辑当场写(`upload.py`、`skills.py`——它们手里就有本次审计结论);此后只有
  `skill_audit/reconcile.py` 写,它从 MR 状态重算,取不到时保持 pending,幂等可重跑。**复核结果只经
  reconcile 落地**,别处不要根据 MR 状态改 status。官方技能导入(`official_import.py`)直接写
  `approved`,见下条。
- **两个触发器,一个收敛函数**:`reconciler` 每 `RECONCILE_INTERVAL`(默认 300)秒扫一遍,这是正确性
  来源——webhook 会丢;`POST /api/audit/reconcile` 供 webhook 调用,只用于缩短延迟。

一个字段属于 git 仓库,当且仅当它是人写的、并且仓库是它被编辑和评审的地方。仓库拥有 SKILL.md 正文与
manifest 里的 name / description / category / tags / version / author / 示例 / inputParams / subSkills;
数据库拥有 rating / downloads / reviewCount / isTrending 与生命周期 status。这些不写入 manifest——快照
写入即过期,而评审要看的是指令变更,数字变动会掩盖它。

# 四、效果

## 内部语料:技能仓里的 46 个真实技能

用最终形态跑(`--policy permissive --use-llm --enable-meta`)。规则由这批样本量出来,不是先定规则再找样本。

| 裁决 | 数量 | |
|---|---|---|
| 上架 | 40 | |
| 复核 | 6 | 全部是真判据,没有一条是故障:2 个版本的同一技能写了"完全信任、无需确认"(`prompt_injection` HIGH)、1 个 SQL 拼接(CRITICAL,只有静态层命中)、1 个连内网主机(`DATA_EXFIL_SOCKET_CONNECT` CRITICAL)、1 个 GUI 死循环(HIGH)、1 个扫描无产出 |
| 拒收 | 0 | |
| 恶意样本 | 拒收 | 语义层与 pipeline 都指向 `command_injection`,两层一致 |

同一批语料走真实接口(`POST /api/skills/evaluate`,因而覆盖输入准备、凭据前置检查、真实裁决模块)再跑
一次:**36 上架 / 8 复核 / 0 拒收**,恶意样本仍拒收,中位 42.2 秒、最大 91 秒。与上表的差别来自模型的
运行间波动——同一份代码与策略,两轮之间就能从 40/6 变成 36/8。

**语义层是这个效果的主要来源。** 同一批语料只跑确定性层(约 5 秒)要复核 22 个(48%);加上语义与仲裁后
复核 6 个(13%)。而且语料里有两条只有语义与仲裁层看得出来的发现——SKILL.md 指示 agent"完全信任、
无需确认"——确定性层对它们完全无感。

**噪声的最大来源是存储格式,不是技能内容。** `artifacts/<name>.zip` 与解压内容并存在工作目录里,扫描器
把压缩包本身报成读不了的二进制(20 个技能)并另报 `ARCHIVE_FILE_DETECTED`(包里夹带压缩包,18 个);41 条"unicode 隐写"
全部命中在 `.pyz` 与 `.zip` 上,是把压缩二进制当文本扫出来的假象。解开并删掉原件后,单次调用输入的中位数
从 7.4 万字符降到 3.1 万。

## 公开基准:OASB 的 skill 子集

来源 `opena2a-org/oasb`(Apache-2.0),样本由该项目标注。只跑其中 `artifactType == skill` 的 290 条。
这组量的是**召回**——内部语料量不了它,因为里面没有恶意样本。

| | 数量 | 结果 |
|---|---|---|
| 已分类恶意 | 93 | **90/93 = 96.8% 未被静默上架**(拒收 4 + 复核 86) |
| 正常(benign + edge_case) | 85 | **84/85 直接上架**;唯一一条被挡是 `LLM_ANALYSIS_FAILED`,与判定无关 |
| 未分类的注册表占位样本 | 112 | 全部上架 —— 内容只有一个名字、没有任何指令,拦下它们才是误报 |

按 OASB 自己的判分口径(命中 = 至少一条 high/critical 的攻击类命中,加固建议类不计):
**精确率 100%,误报率 0%**。

**漏判集中在一处。** 九类里八类全中(凭据外传 11/11、数据外传 10/10、远控心跳 10/10、持久化 10/10、
提权 10/10、提示注入 12/12、社会工程 11/11、供应链 9/9),Unicode 隐写 6–7/10。查下来不是没检出:语义层
与仲裁层都报了,但严重度是 medium/low,而门槛是 high。调整零宽字符阈值并让混淆类在 medium 即拦之后升到
**9/10**。仍漏的 1 条只有 low 级 `obfuscation`,要抓它就得在 low 上设门禁——按本维度对严重度的定义,
low 是"卫生与上下文",不该挡人。这一条记为已知漏判。

## 耗时、成本、并发

一次完整审计的耗时,两种测法(都是同一批 46 个真实技能):

| 怎么测 | 中位 | 最大 |
|---|---|---|
| 批处理脚本直接调扫描器 | 41 秒 | 85 秒 |
| 走真实接口 `POST /api/skills/evaluate` | 42.2 秒 | 91 秒 |

真实接口多出的是输入准备、凭据前置检查与记录落库。确定性层约 5 秒,其余是两次模型调用——语义分析一次、
仲裁一次,没有第三次。

换模型省不了:同一个包、同一条件下 sonnet-5 82.3 秒 / haiku-4.5 83.6 秒 / auto 79.1 秒(这组是在删掉包内
压缩包之前测的,所以绝对值比上表高,但三者之间可比),降 effort 反而更慢(191.6 秒)。
能省的只有缩小输入(等于少看)或不跑仲裁(误报回来)。

管道能承受:`location /api/` 是 `proxy_read_timeout 300s`,前端没有自己的 fetch 超时。编辑路径同样等
80 秒——编辑罕见,而异步会引入"内容已写、判定未出"的中间态。

**token**:单次审计输入约 16K–21K、输出约 1.6K–2.1K(两次调用合计 6.2 万字符;语料 98% ASCII、2% CJK,
按此折算——kiro 不暴露真实计数)。生产当前约每天 2 次上传,量级可忽略。全量重跑 46 个技能约 0.8M–1.0M
输入 token,这是校准的成本。

**并发上限 8**:4/4 与 8/8 全成,16 只成 8。失败在报告里与"语义层没跑成"同形,所以门必须把它当"没查"。
真实流量远低于 8。

**`--use-behavioral` 另有代价**:一个 26 文件的包 29.3 秒且命中数不变;一个 10 文件的包 227.6 秒,多出
一条真发现(`BEHAVIOR_EVAL_SUBPROCESS`:代码里用 `eval` 起子进程)。与文件数无关,是个别大文件让污点分析发散。做法:快分析器总是
跑,behavioral 给预算,跑不完按"这一层未核实"转复核。

## 回归怎么算通过

上面的数字是用批处理脚本直接调扫描器、再单独套裁决规则量出来的——它们是**规格**。回归要验的是**我们的
代码实现了这个规格**,所以必须走真实路径(`POST /api/skills/evaluate`),这样才会覆盖输入准备、凭据前置
检查、真实的裁决模块、状态派生、MR、审计记录与缓存。

**验收标准不能写成"复现某个精确数字"**:同一份代码与策略,模型的运行间波动就能让内部语料从 40/6 变成
41/5。所以:

1. **硬性**:写死的恶意样本必须拒收。
2. **硬性**:85 条公开正常样本与 46 个内部技能中,没有一个被拒收。
3. **区间**:内部语料复核数 ≤ 8/46;OASB 已分类恶意的"未静默上架" ≥ 93%;正常样本误拦 ≤ 2/85。
4. **逐条比对**:与基线相比翻转的技能要人工确认是波动,不是实现走偏。

## 已退役的基准

`skill_audit/*_results.jsonl` 里的 OASB、clawhub 与自有样本成绩出自上一代实现(自建判定器 + 自造类别 +
`strict` 策略)。**在新形态上重跑之前不要引用其中的精确率、召回率、复核率与耗时。** 保留的价值是基准来源
与判分口径可复用。

必须在新形态上确认不退化的一项:只靠零宽字符藏指令的 skill。上一代为此单独加过一层主动扫描,该层随架构
删除,现由扫描器覆盖(依赖 `confusable-homoglyphs`,并有 `unicode_steganography` 与 YARA 隐写规则)。

# 五、上传者与复核者会遇到什么

## 三种结果

| 结果 | 会发生什么 | 上传者看到什么 |
|---|---|---|
| **通过** | 直接上架 | "安全检查通过",可以发布 |
| **可疑** | 入库但不公开,自动开一个 GitLab 复核单(Draft MR)并指派评审人;评审合并后自动上架 | "需要人工复核",完成后给复核单链接 |
| **危险** | 当场拒绝,不入库、不建复核单 | "未通过安全检查" + 参考编号 + 每条命中的位置和原文 |

所以市场里能用的 skill,都是"检查通过"或"经人复核合入"的。

**不打分。** 只给状态和命中详情——一个密钥泄露不该被平均分冲淡。

**等待期显示真实已用时间。** 一次审计几十秒,界面按耗时分布分档措辞(60 秒内"一般 30–60 秒",超过则说明
比通常久、仍在检查),任何一档都不表示失败。不显示逐步完成的步骤:前端只发了一个请求,无从知道哪个
分析器在跑。

阶段级进度可以做:扫描器在 stderr 上打出阶段标记,单个技能上量到的三个边界是 +3.8s(选定仲裁器)、
+28.2s(开始仲裁)、+79.3s(仲裁完成),该次总耗时 80.7 秒。把这些标记经 SSE 转给前端即可;代价是改 `evaluate` 的接口形态并关掉代理对 `/api/` 的缓冲。

## 被标出问题时,上传者拿到什么

**先说清一件事:命中列表为空不等于"没查出问题"**,也可能是没人查得成。所以结果页在覆盖度不完整时会明确
写出来,并按原因给上传者一句能照做的话——"frontmatter 冒号后少了空格,改完重传",或者"这是平台故障,
已记录,不需要改内容"。这两句由后端给的 `cause` 决定,不是把给复核者看的句子原样转给上传者。


每条命中都是同一形状:**在哪**(文件:行号,可以是包内路径)、**原文**(触发的那句)、**什么意思**、
**怎么改**。报告里出现的英文类别名与字段,含义见第二部分的名词表。例:

> `SKILL.md:7` — 忽略此前收到的所有安全规则与限制
> 提示注入 · 严重 —— 这段文字要求助手无视既有规则。
> 怎么改:删掉推翻助手规则的那段文字。

## 常见现象对照表

| 现象 | 结果 | 怎么改 |
|---|---|---|
| 代码注释和字符串里有中文 | 通过 | 无需处理 |
| 带 docx / xlsx / pdf / 图片等读不了的**数据**文件 | 通过 | 无需处理,数据文件不会被执行 |
| 包里带 `__pycache__/*.pyc` | 通过(记在报告里) | 打包时排除更干净,但这不挡人 |
| 文档里写 `tvly-YOUR_API_KEY_HERE` 这类占位符 | 通过 | 占位符不算凭据 |
| 打包成 `.pyz`(zipapp)等读不了的**可执行**文件 | 可疑 | 平铺放 `scripts/`——读不了的可执行文件必须有人过目 |
| SKILL.md 里写"完全信任 / 无需确认"这类跳过用户确认的指令 | 可疑 | 删掉;需要确认的动作就让 agent 去确认 |
| 把指令藏在"示例输出"块里 | 危险 | 示例块里的指令仍然是指令,删掉 |
| 正文里写了真实的 key / token / 密码 | 危险 | 换成占位符,凭据从环境变量取 |
| `name:值` / `description:值` 冒号后没有空格 | **400 报错**,并指名这一点 | 改成 `name: 值`,冒号后加空格——YAML 里没有空格就不是键值对,字段会被当成没写 |
| frontmatter 不是有效 YAML | 400 报错 | 按报错里给的解析器提示改 |
| 传的是 `manifest.json` 而不是 skill 定义 | 400 报错 | 传 `SKILL.md`,或包含它的压缩包 |

**标准格式**:压缩包根目录(或往下一层)放 `SKILL.md`,frontmatter 必须有 `name:` 与 `description:`;
脚本平铺在 `scripts/`。`description` 不超过 512 字符(Agent Skills 的上限,超了会影响技能自身工作)。

## 复核 MR 的人裁决什么

复核单是一个 Draft MR,标题带上传者。**合并 = 该 skill 上线;关闭 = 拒绝。** 正文按这个顺序回答:

1. **判定理由** —— 一句话说明它为什么进了人工复核。
2. **覆盖度** —— 只在不是"全查过"时出现,是复核时**要最先看的一行**:它说这个 skill 是"一点都没被检查过"
   还是"只检查了一部分"。两者都意味着命中表不是全貌,合入前要逐行看一遍 diff。
3. **归属** —— 作者可以修 / 平台侧 / 各占一半,附一句该做什么。平台侧的意思是这不是作者的问题,应当重跑,
   不要凭这次结论决定合不合。
4. **命中表** —— 每条给出规则、类别、严重度、文件行号、命中原文与修复建议。**命中为空时不渲染这张表**:
   一个只有表头的空表什么都没说,而这正是改动前复核者看到的东西(`rp-ai/rp-ai-skill!13`、`!14`)。

不该占用复核时间的东西不进门禁:缺 license、包里带压缩包、`__pycache__`、描述超长这类卫生问题只进报告。

复核实际要裁决的是三类东西:

1. **内容没被完整检查过**(覆盖度那一行会说明是哪种)。最常见的两个:包里有会运行的文件读不出来;
   `SKILL.md` 的 frontmatter 不合格式导致扫描器根本没加载它。
2. **审计自身失败**(超时、某层崩了)。这一类不该由复核者判断内容,交给维护者重跑。
3. **只有一层命中的高危判据** —— 例如静态规则报出 SQL 拼接。拒收要求两层一致,所以这一类通常的结论是
   "让作者改",而不是"不许上线"。

# 六、做不到什么

以下是方案的边界,不是待办。

- **静态扫描可被蓄意规避**:自解压打包、"扫描时正常、事后改坏"的可变外链。结构性盲区,只能拦明显的和
  无意的问题。
- **语义层可能判错**。模型不持有任何工具,但误判与漏判仍会发生;靠人工复核兜底,不能根除。
- **读不了的可执行文件**(`.pyz`、`.exe`、编码不可解的脚本)一律转复核——系统读不懂,只能人看。
  非 UTF-8 编码(如 GBK)的脚本属于此类。
- **记录的上传者身份已经改走 token。** 登录走 LDAP 校验企业账号密码并签发 JWT,站点级中间件要求每个
  `/api/` 请求都带有效 token。上传(`upload.py`)与编辑(`skills.py`)现在都用 `acting_eid(request, ...)`:
  token 里的身份优先,客户端声明只在 `auth_enabled=false` 时兜底,所以已登录的人不能再把上传记到别人名下。
  剩下的例外是 `list_skills` 的可见性过滤仍读客户端头,见 platform-ci 的 ROADMAP。
- **没有发现不等于没有问题**。标注集仍小,召回需要更大样本持续评估。
- **依赖 `kiro-cli acp` 的协议稳定**。kiro 升级改了 ACP,语义层就会失败;缓解只有失败关闭加适配器自己的测试。
- **`--use-behavioral` 默认关闭**,所以需要多步污点分析才能看出的行为目前只靠 pipeline 的单步污点。
- **不收录的判断**:功能欺诈(声称做某事、实际返回写死结果)、反检测规避工具。二者属"行为不当"而非
  "内容危险",不在本维度范围。
- **一个已知漏判**:只用 low 级 `obfuscation` 藏内容的样本(OASB 里 1 条)。
- **SKILL.md 缺 `name:` 的包无法被扫描**,扫描器直接报 `Error loading skill:`,该原因原样透出给上传者。
