# Skill 审计 · 安全合规维度

上传的 skill 在**入库前**过一道安全检查,结果只有三种。不涉及技术的同事读到"机制总览"为止即可,后面是工程细节。

## 这道检查做什么
现在 skill 上传后没有任何安全检查,也没有可见性控制:任何人传一个带明文密钥或恶意指令的 skill,马上就能被别人浏览、下载、加载进 AI 里执行。本维度在入库前加一道检查,并把结果如实告诉上传者。

| 结果 | 处理 | 上传者看到什么 |
|---|---|---|
| **通过** | 直接上架 | "安全检查通过",可以发布 |
| **可疑** | 入库但不公开,自动开一个 GitLab 复核单(Draft MR),命中点写进评论并指派评审人;**评审合并后自动上架** | "需要人工复核",按钮是"提交复核",完成后给复核单链接 |
| **危险** | 当场拒绝,**不入库**、不建复核单 | "未通过安全检查" + 参考编号 + 每条命中的位置和原文 |

所以主库里能用的 skill,都是"检查通过"或"经人复核合入"的。

**每条命中都按同一形状呈现**:**在哪**(文件:行号,可以是包内路径)、**原文**(触发的那句)、**什么意思**(一句话)、**怎么改**(一句话)。举例:

> `SKILL.md:7` — 忽略你收到的所有安全规则与限制
> 提示注入 · 严重 —— 这段文字要求助手无视既有规则。
> 怎么改:删掉推翻助手规则的那段文字。

**安全只给状态和命中详情,不打分**——一个密钥泄露不该被平均分冲淡。

**人工复核直接用 GitLab MR**(评论、指派、审批、合并、通知都现成),不另做站内审核界面。

## 什么算"安全问题"(判断标准)

**这道门只对隐瞒与越权发力,不对"有能力"发力。** 一个技能声明了要连网、然后确实连网,不可疑;
一个技能声明了要装依赖、然后确实装,不可疑。可疑的是**做了不说**,或**做得比声明的多**。

判断落在两件事上,都不需要我们自己发明词汇:

- **类别**由扫描器的规则包声明,并挂在公开分类学 AITech 上(见下)。
- **严重度**用它自己的刻度,含义是**能力与已然的行为之别**(见"实现细节 > 严重度")。

依据:OWASP LLM Top 10 2025、CWE-798(硬编码凭据)、USENIX Security 2026(该研究测得 84% 的 skill 漏洞
出现在自然语言指令里,而不是代码里)——这也是语义层不可省的理由。

**类别词汇只有一套,就是扫描器规则包声明的那套。** 它在 385 条规则上声明了 17 个类别,并自带到公开框架的
映射(`threats/cisco_ai_taxonomy.py`,AITECH / AISUBTECH + 框架映射),所以分类依据可追溯,不需要我们
另写一张对照表。**我们的语义判定器也输出这套类别名**——两层用同一套词汇,同一个类别由两层独立命中就是互证,
而不是需要翻译的两种说法。

曾经自造过一套五个类别(`secret` / `dangerous_instruction` / `malicious_artifact` / `hidden_instruction` /
`prompt_injection`),与工具的词汇只有一个名字重合,于是中间必须有一次翻译;那次翻译把 `obfuscation` 变成
红线类"隐藏指令"(中文注释因此被判危险),又把 `TOOL_ABUSE_UNDECLARED_NETWORK`、`DATA_EXFIL_SOCKET_CONNECT`
压成"未分类"。自造词汇同时也更粗:工具有 `agent_manipulation`(99 条规则)与 `tool_poisoning`(24 条),
而"操纵 agent"正是恶意技能要做的事。

参与门禁的类别与处理,即下文"裁决"那张表;界面上只显示面向用户的检查项名称,不显示类别标识符与框架编号。

**展示是展示,不是第二套语义。** 界面上的中文检查项名称由一张展示映射提供,**遇到没有映射的类别时直接显示
工具自己的 `title`**,不猜、不归到"其他"。这张映射只影响措辞,不影响任何判定。

## 机制总览:查哪些层面、怎么查

上传的内容会被完整展开——SKILL.md 正文,以及压缩包里的每个文件——然后**跑一次扫描器**,它内部按自己的
架构依次跑这些分析器,出一份统一报告:

| 分析器 | 看得到什么 | 看不到什么 |
|---|---|---|
| static + YARA | 固定模式:硬编码凭据、命令执行、下载即执行、不可见字符、同形字、可执行与编译产物 | 句意(缺上下文的关键词匹配,是误报的主要来源) |
| pipeline | 命令链污点(网络输入流向执行) | 单条命令之外的意图 |
| bytecode | `.pyc` 完整性 | 源码语义 |
| behavioral(给预算) | Python AST + 污点跟踪的多步行为 | 非 Python;个别大文件会让它发散 |
| llm(模型是 kiro) | SKILL.md、配置与打包文本的**意图**,**以及代码与声明是否一致** | 超出它自己上下文预算的部分(会报 `LLM_CONTEXT_BUDGET_EXCEEDED`) |
| meta(模型是 kiro) | 二次过审:对着源码核实每条命中、合并同源、剔误报、排优先级 | 不找新威胁(它自己的 SOP 明令) |

**类别与严重度原样透传,不改名。** 报告里还带 `analyzers_used`,哪一层没跑成它自己会说。

**检测各自独立,仲裁刻意看全部。** 曾经的写法是"两层不互相通气":确定性层的结论不进语义层的提示词,
理由是模型会附和提示里已有的立场、把类别名复述成自己的判据。那个顾虑是真的,但断供不是解法——它同时
掐掉了降误报的唯一手段。分三段才对:

1. **检测**:各分析器独立跑,互不知道对方结论。
2. **仲裁**:一次二次过审,**看到全部命中 + 完整文件内容**,职责只有校验、合并、剔误报、排序,**不找新威胁**。
   附和用"对着源码核实"来治:每条命中都要回到文件里确认代码是否真的在做它声称的事。
3. **裁决**:把仲裁后的结果翻译成市场决定。

实测这一段的价值:46 个真实技能上,只跑确定性层要复核 22 个(48%),加上语义与仲裁之后是 6 个(13%),
而**整个语料里唯一两个真正危险的发现正是仲裁层给出的**(见"实测")。

**结论怎么定。** 规则由 46 个真实技能加一个写死的恶意样本量出来,不是推想的:

1. **卫生类永不参与门禁** —— 缺 license、包里带压缩包、`__pycache__`、描述超长。这些不说明任何行为,
   只进报告给作者。
2. **读不了的文件只有在它是可执行文件时才拦** —— `.bat/.ps1/.pyz/.exe/.pyc` 这类读不了必须人看;
   读不了的**数据**文件(docx/xlsx/pdf/图片)不拦,它们不会被执行。
3. **门槛是 high** —— medium 进报告,不挡人。严重度含义见下(能力 vs 已然的行为)。
4. **拒收要求两个独立层对同一类别一致** —— 拒收是唯一不可逆的动作。只有静态层命中的 critical 转复核,
   不拒收;确定性层与语义层都指向同一类别时才拒收。
5. **任何一层没跑成 = 复核** —— 包括扫描没有产出结果、语义层失败、超出上下文预算。
   "我们没查"和"查了没发现"是两件事。

落在真实语料上:**40 个上架 / 6 个复核 / 0 个拒收**,恶意样本拒收。6 个复核里 2 个是语义层自己没跑成
(可修),1 个是扫描无结果,1 个是只有静态层命中的 SQL 注入写法(交作者改,不该拒),
2 个是同一个技能的两个版本在 SKILL.md 里写了"完全信任、无需确认"。

**判据与结论必须同源。** 每条命中都带 `snippet`(命中原文)与 `location`,能在被审内容里找到;
仲裁层的职责之一就是拿命中回到文件里核实代码是否真的在做它声称的事,核不实的剔为误报。
这不再由我们自己实现——曾经写过一层"判定器复述我们的类别名就丢弃"的过滤,那是自建编排时的补丁。

**两条一定要知道的原则:**
- **模式匹配的断言要经过核实才作数**。它会把"非 ASCII 与 ASCII 混排"报成伪装攻击,而中文注释不是;
  也会把压缩包与 `.pyz` 当文本扫出"unicode 隐写"。核实由仲裁层做,核不实的剔除,**核不了的降为复核**。
- **某层没跑成时如实说"未能核实"**,并把这次转人工复核,而不是当作通过。**这条对静态层与语义层同等成立。** 曾经只在语义层落地:静态扫描器的超时被吞掉、当作"没跑",审计照常出结论。实测一个真实包扫完需要 **232.7 秒**,而代码里的上限是 120 秒,于是它的 `DATA_EXFIL_SOCKET_CONNECT`(CRITICAL)、`TOOL_ABUSE_UNDECLARED_NETWORK`、`UNANALYZABLE_BINARY` 三条命中一条都没有进记录。**超时不是"通过",是"没查"。**

- **判定要能复现。** 审计记录要存**模型名 + 扫描器版本 + 策略指纹**。少了它们,今天的结论明天无法解释,
  规则升级带来的判定变化也无法与内容变化区分。
- **用途公开声明的工具类 skill 转复核,不硬拒**。凭据代管、改 agent 配置、安全测试、混沌工程与故障演练、运维清理这类 skill,其声明用途本身就是那项能力,会命中"危险操作"的字面特征。判断依据是**是否声明并可核对**,不是这个动作听起来危不危险;只有隐瞒行为、外传数据凭据、或作用于用户无权处置的系统才升级为红线。

**为什么"把指令挪到别的文件"不管用**:agent 会按 SKILL.md 的指引去读 `reference/notes.md`、`mcp.json` 这类文件,所以它们里的指令与写在正文里等效,一并送语义层审。实测同一段"定时拉取远程代码并执行"的内容,放在 `scripts/setup.py` 由静态层判危险,放在 `mcp.json` 或 `reference/notes.md` 由语义层判危险,三处结论一致。

## 常见命中与怎么改

| 现象 | 结果 | 怎么改 |
|---|---|---|
| 包里带 `__pycache__/*.pyc` | **通过**(记在报告里) | 打包时排除更干净,但这不挡人 |
| 打包成 `.pyz`(zipapp)等读不了的可执行文件 | 可疑 | 平铺放 `scripts/`——读不了的可执行文件必须有人过目 |
| 带 docx / xlsx / pdf / 图片等读不了的**数据**文件 | **通过** | 无需处理。数据文件不会被执行 |
| 代码注释和字符串里有中文 | **通过** | 无需处理。中文可见、与 ASCII 不混淆,不算隐藏指令 |
| 文档里写 `tvly-YOUR_API_KEY_HERE` 这类占位符 | 通过 | 无需处理,占位符不算凭据 |
| 把指令藏在"示例输出"块里 | 危险 | 示例块里的指令仍然是指令,删掉 |
| 传的是 `manifest.json` 而不是 skill 定义 | 400 报错 | 传 `SKILL.md`,或包含它的压缩包;manifest 由系统生成 |

**标准格式**:压缩包根目录(或往下一层)放 `SKILL.md`,frontmatter 必须有 `name:` 和 `description:`;脚本平铺在 `scripts/`。

## 实现细节

### 边界:哪些是工具的,哪些是我们的

分界线是**策略与集成**。越过它就会出现两份会各自漂移的真相。

| | 归谁 | 表现形式 |
|---|---|---|
| 规则目录、类别名、严重度、阈值、良性白名单、误报抑制、置信度 | **扫描器** | 策略文件 + `--taxonomy` / `--threat-mapping`,由我们覆盖需要的项 |
| 什么时候扫、扫哪个目录、超时多久、失败怎么办 | 我们 | 集成代码 |
| 把它的命中翻译成市场决定(上架 / 复核 / 拒收) | 我们 | 只有这一步是本平台的策略:**哪些类别参与门禁** |
| 写入门、复核工作流、事实记录、报告呈现 | 我们 | 集成代码 |
| 语义与仲裁 | **扫描器编排,kiro 出模型** | 它的 `llm_analyzer` 与 `meta_analyzer` 需要一个 OpenAI 兼容端点。本环境没有任何托管 provider 的 key,但有 kiro-cli 的登录态,而 `kiro-cli acp` 说 ACP。中间放一个约 190 行的适配器把 `/v1/chat/completions` 翻成 ACP,于是**这两层由它自己编排,模型是 kiro** |

**一次调用,不自建编排。** 审计 = 跑一次扫描器,读它那一份报告。检测、语义、仲裁都在它内部按它自己的
架构完成;我们不再自己拼提示词、自己切分输入、自己派生两层状态。我们只剩两样东西:

- **适配器**:`/v1/chat/completions` → `kiro-cli acp`。模型**不带任何工具**——它只收文本、只回 JSON,
  比原先那个持有 `fs_read` 的判定器 agent 权限更小。
- **裁决**:读报告,决定上架 / 复核 / 拒收,写仓库,记事实。**这是唯一一张我们维护的表。**

曾经考虑过反过来:写一个 skill 让 agent 按 SOP 自己去调扫描器。不采用,理由是权限与确定性——那样 agent
必须持有执行权限才能跑扫描器,而它同时在读不可信内容;并且"确定性层到底跑了没有"会变成取决于模型是否
照做。一道门不能让"我们真的扫过了吗"成为模型行为问题。

裁决层**不回头修改检测层的类别名或严重度**——那是策略数据的事。想调轻重就改 `severity_overrides`,
想关噪声就改 `disabled_rules`,一处、可 diff、可复现。

裁决表里必须由我们提供的语境只有一件:**目的地是不是我们自己的内网。** 工具认得 `socket.connect` 的形状,认不出 `plm.internal.ericsson.com` 是自家主机——它的 `exclude_patterns` 只排除了 localhost。所以 `data_exfiltration` 到内网是预期行为、到外网才是红线,这条判断按定义属于我们,不属于工具。

三条自洽性约束,都要有测试:

1. **没见过的类别默认转复核。** 工具升级会加新规则、新类别;裁决表遇到不认识的类别时落到"未核实",不静默放过。
2. **某个分析器没跑完 = 未核实 = 转复核。** 不区分是超时、崩了还是没装。
3. **判定可复现。** 审计记录存**模型名 + 扫描器版本 + 策略指纹**(策略里的 `attach_policy_fingerprint`
   提供后者)。原先存的 `rules.md` 哈希随自建提示词一起消失。

**严重度的刻度也取自工具,含义按它的规则赋值反推,不自己发明。** 曾经在提示词里只把
`critical|high|medium|low` 列成枚举、从不定义,然后拿这个没有刻度的数去做门禁判断。工具的赋值方式是一致的:
`DATA_EXFIL_NETWORK_REQUESTS`(出现网络调用原语)是 MEDIUM,而 `DATA_EXFIL_HTTP_POST`(POST 的目标或载荷
里出现凭据字样)是 CRITICAL;`PROMPT_INJECTION_IGNORE_INSTRUCTIONS` 是 CRITICAL。可以读出来的分界是
**能力与已然的行为**:

| 级别 | 含义 | 例 |
|---|---|---|
| critical / high | 文本或代码呈现的是**行为本身**——有对象、有载荷、有目标地址 | 把凭据 POST 到某地址;要求助手忽略既有规则 |
| medium | 只呈现**能力**,没有指向这次行为的证据 | 用了网络原语;声明之外的网络访问 |
| low / info | 卫生与上下文,不指向任何行为 | 描述超长;夹带了脚本;未知二进制 |

这条分界与本维度的判据一致:门对**隐瞒与越权**发力,不对**有能力**发力。所以它同时是判定器给分的规则,
也是裁决表读分的规则,两边不会各自漂移。

### 工具与调用方式
- 密钥:检出本身交给扫描器——它有 `hardcoded_secrets` 规则族与 promptguard 的 `secret_providers.yaml`,
  覆盖面比我们那 23 个检测器广,所以**自建的检出层退役**。

  但有一个属性会随之丢掉,必须显式处理:原先两层都在**把文本交给模型之前脱敏**,密钥不外泄给模型。
  改成扫描器自己读文件、自己调模型之后,我们不再经手提示词,**一个写在 skill 里的真实凭据会被原样送进
  语义层**。模型跑在我们自己的额度上、内部环境,但"凭据不该离开它所在的位置"这条不因为对方是自己人而
  改变。所以保留一层**极小的正则红线前置检查**:它的目的不是覆盖面,而是**在调用扫描器之前**就拦下明确
  的真实凭据(命中即拒收),让它根本没有机会进入任何提示词。这一层不参与其他判断。
- 静态:Cisco AI Defense `skill-scanner`,只用不需要 key 的静态分析器(static / bytecode / pipeline);它的 LLM 与 VirusTotal 分析器需要 key,本版本不启用。

  **策略用 `permissive` 作基线。** 官方的选择树是:不受信任/外部技能用 `strict`,普通 CI 用 `balanced`,
  **受信任的内部技能用 `permissive`**。本平台是内部市场,作者是记录了 EID 的同事,内容还要过一次 MR 复核,
  这道门是兜底而不是防同事,所以取 `permissive`。

  曾经用的是 `strict`,那一档的定位写明是"untrusted / external skills and compliance audits"。实测它的代价:
  一个真实中文技能在 strict 下 14 条命中、其中 **12 条是 `HOMOGLYPH_ATTACK`**(命中在 `.py` 的中文注释上),
  balanced/permissive 下同一个包只有 1 条;而对写死的恶意样本,三档**抓到的完全一样**。
  strict 一次性关掉 `demote_in_docs`、`demote_instructional`、`check_known_installers`、四个
  `compound_fetch_*` 过滤器,并把 `known_installer_domains` 清空、`benign_pipe_targets` 砍到两条,
  同时收紧 CJK/同形字阈值——**多出来的全是噪声,一条真问题都没多抓。**

  `balanced` 与 `permissive` 在 46 个真实技能上的差别未逐一测量;两者对恶意样本的检出相同,
  取更宽的一档与"兜底"的定位一致。

  **自定义策略与默认值合并时,列表是替换而不是追加。** 覆盖任何白名单都必须整份重写,否则会静默缩小它。

  **策略是数据,不是代码。** 规则目录、类别、严重度、阈值、白名单、误报抑制、置信度都由扫描器的策略文件与 `--taxonomy` / `--threat-mapping` 表达(`skill-scanner generate-policy` 可导出默认值,`severity_overrides` 调严重度,`disabled_rules` 关噪声规则)。我们不在 Python 里重写一份:手写的丢弃名单与类别改名表会与工具的规则目录漂移,而漂移是静默的。

  **它的类别原样透传,不改名。** 曾经把 `obfuscation` 改名成我们的红线类 `hidden_instruction`、把 `BINARY_FILE_DETECTED` 改名成 `malicious_artifact`、其余一律归入"未分类"。改名有两个后果:中文注释触发的 `HOMOGLYPH_ATTACK` 变成"刻意隐瞒"而直接判危险;而 `TOOL_ABUSE_UNDECLARED_NETWORK`(未声明的网络访问,正是本维度关心的越权)、`DATA_EXFIL_SOCKET_CONNECT`、`UNANALYZABLE_BINARY` 这些**说得比我们准的类别**被压成"未分类"或整类丢弃。

  **按规则取舍,不按类别整片丢。** 原先把 `policy_violation` 整类过滤掉,连带丢掉两条不该丢的:`UNANALYZABLE_BINARY`(读不了的文件必须由人看)与 `MANIFEST_DESCRIPTION_TOO_LONG`(Agent Skills 对 `description` 有 512 字符上限,超了会影响技能自身工作)。

  **每条命中自带 `snippet`(命中原文)与 `remediation`(怎么改),必须透传。** 不读这两个字段,记录里就只剩"某文件某行命中了某规则",作者无法答复,复核者也无法判断。
- 本环境禁用 MCP,所以确定性工具都以进程内库或 CLI 方式调用、直接取结构化结果,由流水线驱动,不经过判定器。
- 静态层报"隐藏指令"时按我们的定义复核后才采信:零宽字符、双向控制符、以及形似 ASCII 的字母(西里尔、希腊、全角**字母与数字**——全角标点是正常中文排版,不算)。核实要能读到它指向的内容:它用 `outer.zip!/inner.py` 指向压缩包内的文件,只按文件系统路径查读不到包内文件,而代码通常就打在包里。读不到时降为复核,不硬拒。
- 附件层:源码脚本交静态分析按内容判断,不因"带了脚本"就一律转复核(代码里记作 `bundled_code`,只进报告作上下文,不参与门禁)(真实语料里约 20% 的 skill 带附件,一律转复核等于把多数正常上传压给评审);**编译与二进制文件一律转复核**,独立于静态分析器运行,因为复核靠人读改动,二进制读不了。

### 接进上传流程(判定与入库解耦)
判定和入库是两件事,分开做:"这个 skill 安不安全"的判断,不应该和"把它入库"这个动作绑在一起。
- **判定(纯函数)** `audit_skill(内容) → {状态, 命中详情}`:跑确定性扫描器 + 语义节点,输出 通过/可疑/危险 + findings。无副作用、幂等。
- **evaluate 接口**:调 `audit_skill`,返回状态 + 命中详情,**不入库**。给上传向导的"评估"步用,让用户在发布前看到真实结论(状态 + 命中详情,不打分)。
- **publish(upload)接口**:入库这个动作。**内部再调一次 `audit_skill` 做权威门禁**(不信任前端 evaluate 的结果,防止有人绕过前端直接调 publish),再按结果分流:
  - 危险 → HTTP 422,不入库、不建 MR,返回 `{状态, reference, 命中详情}`。
  - 通过 → 提交到主分支,上线。
  - 可疑 → 提交到复核分支 + 开 Draft MR(见下),不进主分支。
- **编辑(`PUT /api/skills/{id}`)走同一道门。** 它写的是同一个仓库里的同一份内容,所以分流规则与 publish 一致:危险 → 回滚这次编辑、只留审计记录、422;可疑 → 复核分支 + Draft MR,并把 status 退回 pending(没被复核过的内容不算已发布,即使这个技能之前已上架);通过 → 主分支。这条路径原先没有被设计,于是它直接写仓库、一次审计也不跑——**门被挂在了上传路由上,而不是挂在"把内容写进仓库"这个动作上**,后加的路由自然绕过去。
- **门挂在动作上,不挂在路由上。** 唯一的写入口 `skill_storage.store()` 必须收到审计结论才肯写,并且自己拒绝两件事:写入被判危险的内容;把待复核的内容写到主分支。以后新增写入路径时忘了审计是**签名错误**,不是安全事故。
- 门禁强制在 publish 这一侧(服务端):页面用户无 GitLab 权限、无法绕过直接 push,不需要 pre-receive 钩子;evaluate 只是同一函数的 UX 预览,不承担门禁。
- evaluate 与 publish **复用同一个 `audit_skill`**,判定逻辑只有一份;用内容哈希缓存(同内容短时间内复用判定结果)避免语义判定器跑两遍。
- 确定性检查(密钥/附件)同步跑(快);语义检查放在向导评估进度位(约 10s)。判定器不可用/超时时 **fail-closed**:该次转人工复核,而非放行。
- **但跑不起来的审计不能改变已经发布的东西。** 上面那条 fail-closed 的代价落在提交者身上,前提是还没有东西上线。对一个已上架的技能提交新版本(重新上传或编辑)时,同样的反射会把它退回 pending、从市场撤下——原因只是某个服务当时不通,代价却落在所有正在用它的人身上。这种情况下什么都不改,返回 503 让人稍后重试。规则由"有没有东西已经发布"推出,不是给某条路由开的特例。

### 可疑怎么走审核(GitLab MR)
- 后端用有写权限(api scope)的 GitLab token,把该版本提交到分支,开一个 Draft MR(如 "skill under review: <name>"),把每条命中(类别 / 证据 / 依据)作为 MR 评论贴上,指派评审人(EZHGMIO)。
- 评审在 MR 里定:同意 → 合并(skill 进主库、上线);不同意 → 关闭 MR(不上线)。评论、线程、审批、合并、通知都用 GitLab 现成的,不自建审核界面,也不需要额外审计表。
- MR 开在 skill 仓(存 skill 的那个仓库;示例里的 portal-be 只是形态参考)。

### 仓库和数据库各自拥有什么
一个字段属于 git 仓库,当且仅当它是人写的、并且仓库是它被编辑和评审的地方。

- **仓库拥有(人写)**:SKILL.md 正文,以及 manifest 里的 name / description / category / tags / version / author / isFree / capabilityFull / 示例 / inputParams / subSkills / cases。
- **数据库拥有(测量或派生)**:rating、ratingDist、reviewCount(评价的聚合)、downloads(下载计数)、isTrending,以及生命周期 status。这些**不再写入 manifest**:快照写入即过期,要保持准确就得每次下载都提交一个 commit;评审要看的是指令变更,数字变动会掩盖它;任何"仓库 → 数据库"的导入路径也可能用过期值覆盖真值。导入侧仍兼容读取旧 manifest 里的这些键。

### 状态与分类怎么建模
状态分三层,规则是:派生字段必须能从事实重算出来。

- **事实**(不可变、只追加):审计事件与命中证据(`rp_ai_skill_audit_record` + `rp_ai_skill_finding`);复核决定由 GitLab 的 MR 状态承载;哪个版本在线由 git 仓库决定。
- **唯一的生命周期闸门**:沿用既有的 `rp_ai_skill.status`(pending / approved / rejected),它本来就在 API 契约里。通过 → approved(直接上架);可疑 → pending(等复核 MR);危险 → 不入库。MR 合并 → approved;MR 关闭 → rejected。**不再另立一条审批轴。**
- **展示缓存**:`audit_state` 只保存当前版本最近一次判定结果,用于说明"为什么还在 pending",**不作闸门**。
- **唯一写入者**:`skill_audit/reconcile.py`,从事实重算上面两个字段;MR 状态取不到时保持 pending(fail-closed)。幂等,可随时重跑。
- **两个触发器,一个收敛函数**:`reconciler` 服务每 `RECONCILE_INTERVAL`(默认 300)秒扫一遍,这是正确性来源——webhook 会丢(投递失败、重启、网络),只靠事件的系统会静默漂移;`POST /api/audit/reconcile`(用 `AUDIT_WEBHOOK_TOKEN` 校验)供 GitLab webhook 调用,只用于缩短延迟。两者调用同一个函数,不存在两条路径。


### 判定用哪个模型
- **钉死 `claude-sonnet-5`,不用 `auto`**:`auto` 会按任务自动换模型,而门禁要对同一输入给出同一结论,
  并且判定要能归因到具体模型。实测换模型不影响耗时(`claude-sonnet-5` 82.3s、`claude-haiku-4.5` 83.6s、
  `auto` 79.1s),但**影响判定**:同一个真实包在两个模型下的命中数不同。所以校准必须在钉死的模型上做。
- **模型名必须在启动时校验。** `kiro-cli chat --model <不存在的名字>` 会报错并列出可用模型,但
  **`kiro-cli acp --model <不存在的名字>` 静默接受**,打错一个字就会静默用默认模型,归因随之失效。
- **拒收不再靠第二个模型复核。** 曾经的做法是"即将判危险时再问一次 `claude-opus-5`,两者不一致就降为
  复核"。那是自建编排时的手段;改成一次调用扫描器之后,同一个判据由**确定性层与语义层两个独立层给出**
  才拒收(见"结论怎么定"第 4 条),这比问同一家模型的另一个代际更强。若需要抵抗模型的运行间波动,
  扫描器自带 `--llm-consensus-runs N`(跑 N 次只保留多数一致的命中),那是它的机制,不是我们再写一遍。

### 语义层与仲裁层怎么跑
本环境没有任何托管 provider 的 API key,但有 kiro-cli 的登录态。扫描器的 `llm_analyzer` 与 `meta_analyzer`
需要一个 OpenAI 兼容端点,而 `kiro-cli acp` 说 ACP,所以中间放一个约 190 行的适配器:

- `POST /v1/chat/completions` → 起一个 `kiro-cli acp` 进程 → `initialize` / `session/new` / `session/prompt`
  → 收集 `agent_message_chunk` 的文本 → 按 Chat Completions 形状回包。
- **一次请求一个进程**:一次审计不该看到另一次审计的任何东西。
- **模型不带任何工具**(`--trust-tools=`,并拒绝 `session/request_permission`)。它只收文本、只回 JSON,
  比原先那个持有 `fs_read` 的判定器 agent 权限更小——**注入也没有可用的手段**。
- 提示词、输出 schema、注入防护(`<!---UNTRUSTED_INPUT_START--->` 定界)、误报过滤的 SOP 全部由扫描器
  自带并由它注入,我们不再维护自己的 `rules.md`。

环境变量:`SKILL_SCANNER_LLM_PROVIDER=openai`、`SKILL_SCANNER_LLM_BASE_URL=<适配器>/v1`、
`SKILL_SCANNER_LLM_API_KEY=<任意>`、`SKILL_SCANNER_LLM_MODEL=openai/claude-sonnet-5`。
**模型名要带 `openai/` 前缀**,否则仲裁那条路会因 litellm 缺 provider 而失败,而主分析那条路不会——
两条路的失败方式不同,只测一条会漏。

### 实测

#### 线上语料全量:技能仓里的 46 个真实技能

用最终形态跑(`--policy permissive --use-llm --enable-meta`,模型钉 `claude-sonnet-5`)。这是校准的依据:
规则由这批样本量出来,不是先定规则再找样本。

| 裁决 | 数量 | |
|---|---|---|
| 上架 | **40** | |
| 复核 | **6** | 2 语义层自己没跑成、1 扫描无结果、1 只有静态层的 SQL 注入写法、2 同一技能两版本写了"完全信任、无需确认" |
| 拒收 | **0** | |
| 恶意样本 | 拒收 | 语义层与 pipeline 都指向 `command_injection`,两层一致 |

**这 80 秒买到的是准,不是严。** 只跑确定性层(约 5 秒)要复核 22 个(48%),而整个语料里唯一两个真正
危险的发现——`autonomy_abuse: SKILL.md instructs 'Full trust / no confirmation' bypassing agent safety
controls`——**只有仲裁层给得出来**,确定性层完全看不到它。

**噪声的最大来源是我们自己的存储格式,不是作者。** `artifacts/<name>.zip` 与解压后的内容并存在工作目录里,
扫描器把压缩包本身报成"读不了的二进制"(20 个技能)并另报 `ARCHIVE_FILE_DETECTED`(18 个);41 条
"unicode 隐写"全部命中在 `.pyz` 与 `.zip` 上,是把压缩二进制当文本扫出来的假象。**解压后不要留压缩包。**


#### 以下基准量的是**已退役的自建判定器**,换架构后必须重跑

下面三组数字(OASB、clawhub、自有样本)出自"我们自己编排一套流水线 + `rules.md` + 自造类别 + `strict`
策略"的实现。那套实现正在被替换,**所以这些数字不能用来描述现在的方案**,保留的原因只有两个:基准来源与
判分口径可以复用,以及它们记录了当时确实存在的能力。**在新形态上重跑之前,不要引用这里的精确率、召回率、
复核率与耗时。**

拿公开基准测,并且用基准自己的判分口径,这样数字能和别的扫描器放在一起看。

##### 和公开扫描器比:OASB 基准

来源 `opena2a-org/oasb`(Apache-2.0),专门评测 agent skill 扫描器,样本由该项目标注。它同时公布了榜单成绩和判分口径,所以我们按它的口径算自己的分:**命中 = 至少产出一条 high/critical 的攻击类命中,加固建议类不计**(它自己的理由:`allowedTools:["*"]` 这类信号在几千个正常配置上也会响,不能区分恶意)。

| | 样本 | 精确率 | 召回率 | 误报率 |
|---|---|---|---|---|
| **本方案**(skill 类型:93 恶意 + 68 正常) | 161 | **100%** | **97.8%** | **0%** |
| HMA 全流水线(榜单发布值) | 4,245 | 83.2% | 82.6% | 1.16% |
| HMA 纯静态规则(榜单发布值) | 4,245 | 99.3% | 51.1% | 0.03% |

**分类别命中(已分类的恶意 skill)**

| 类别 | 命中 | | 类别 | 命中 |
|---|---|---|---|---|
| 凭据外传 | 11/11 | | 提示注入 | 12/12 |
| 数据外传 | 10/10 | | 社会工程 | 11/11 |

提权那 2 条不是漏判,是**策略差异**:它们在正文里明写自己要提升管理员权限,按我们"声明即用途者转复核、隐蔽者才红线"的原则判为可疑、转人工复核;基准按更严的口径标成恶意。按"是否阻止了静默上架"来看(拒绝 + 可疑都不会直接公开),**93 条已分类恶意 skill 一条都没放过去**。

**语料里还有 112 条标为恶意、但内容只有一个名字的注册表占位样本**,例如:

```
---
name: mathews-tom/praxis-skills/linkedin-post-style
description: Agent skill: linkedin-post-style
---
# mathews-tom/praxis-skills/linkedin-post-style
Agent skill: linkedin-post-style
```

没有任何指令可判,我们全部放行;拦下它们才是误报。榜单发布的成绩同样不含这批样本(发布时用的是已分类集合),所以上表也把它们排除,并单列说明。

**这次跑分查出并修掉一个真缺陷**:隐藏字符原先只在静态工具报出可疑时才去核实,静态工具不报就没人查,
一份只靠零宽字符藏指令的 skill 会直接通过。当时的补法是我们自己主动扫一层(unicode 隐写从 6/10 到 10/10,
408 条真实 skill 上新增误报 0 条)。**那一层随架构删除**:扫描器依赖 `confusable-homoglyphs`,并有
`unicode_steganography` 与 YARA 的隐写规则,由它自己覆盖;重跑时要确认这一项没有退化。

##### 日常成本:408 个真实 skill

来源 `OpenClaw/clawhub-security-signals`(MIT),取自真实 skill 市场。这组不用来算准确率(它的标注出自扫描器,不是人工),只用来量成本:在其中 250 个正常 skill 上,**没有一个被拒绝**,**转人工复核 8%–10%**(同一批样本两次运行分别是 20 条和 26 条)。也就是每 100 次正常上传,大约 8 到 10 次需要有人看一眼。命中原因主要是正文出现危险操作类措辞、附件带脚本或编译产物,以及少量我们不归类、交人判断的信号。

同一份数据的论文侧测量(Holzbauer et al., arXiv:2603.16572,23.8 万个 skill)给出了各扫描器在真实市场上的命中率,可以看出这个 8%–10% 处在什么位置:

| 扫描器 | 真实市场命中率 |
|---|---|
| Socket | 3.8% |
| Snyk | 7.7% |
| **本方案** | **8%–10%(其中硬拒 0%)** |
| agent-trust-hub | 13.8% |
| Cisco Skill Scanner | 14.0% / 16.7% |
| GPT 类判定器 | 27.3% / 38.8% |
| VirusTotal | 36.2% |
| OpenClaw Scanner | 41.9% |

命中率高不等于好:那篇论文同时测出 5 个扫描器在 2.7 万个 skill 上的结论**一致率只有 0.12%**,说明这类工具彼此严重不一致,命中多的那几个把大量正常 skill 也算了进去。我们这一栏的意义在于:成本落在低位,而其中**硬拒为零**——正常 skill 不会被门禁挡死,最坏是等一次人工复核。

| `scripts/setup.py`(代码) | 危险 —— 静态层命中,给出文件与行号 |
| `mcp.json`(配置) | 危险 —— 语义层命中 |
| `reference/notes.md`(说明文档) | 危险 —— 语义层命中 |

后两处在把打包文本文件纳入语义层之前是**通过**的。同时验证:一个正常的多文件包(说明 + 配置 + 脚本)仍然通过。

**复现:** `python3 skill_audit/run_oasb_v2_eval.py`(公开基准,含上面的对照表)、`run_clawhub_eval.py`(真实语料)、`run_regression.py`(定向回归);每次判定的原始结果在同目录 `*_results.jsonl` 里。

#### 边界:这些数字回答不了的问题

- **中文能拦得住吗?** 不知道。公开基准全是英文样本;中文侧只有 16 个真实中文 skill(没有误报)和 4 个自造坏样本,不足以下结论。
- **能和榜单直接比名次吗?** 不能。逐样本结果没有公开,我们只能在自己受理的制品类型上按同一口径算分。
- **同一份内容每次判定都一样吗?** 不完全一样。模型已钉死,但判定器仍有运行间波动:同一批 250 个真实 skill,两次运行的复核率是 8.0% 和 10.4%。确定性层(密钥、静态规则、隐藏字符)不受影响。
- **附件里的东西测过吗?** 正文测过;附件层只有上面那次定点检查,没有成规模的基准。
- **换判定模型后这些数字还算吗?** 不算,要用同一套基准重跑。
- **判定器挂掉会怎样?** 实测中出现过不可用。这时不会静默放过,而是按"未能核实"转复核或拒绝。
- **这套部署方式验证过吗?** 演示环境验证过;云端隔离部署与服务器侧凭据还没测。

### 前端触点(独立仓 rp-ai-portal-fe)
后端已经承担了大部分:未公开的 skill 在 list 接口就被过滤,前端收不到;人工复核走 GitLab MR,不需要站内评审页。前端改的是上传向导,四屏:

1. **上传**:填表单(文件 + 名称 + 部门),点"开始安全检查"。
2. **检查中**:这段期间真实调 `evaluate`(只判定、不入库),**约 80 秒**。不能再用一个约 10 秒的动画糊过去:
   要按阶段如实显示(静态 → 语义 → 仲裁),否则用户会以为卡死。
3. **报告**:按后端返回的固定检查项集合渲染,**通过的检查项也列出**,让作者看到系统查了什么。每项给出它在查什么;命中项展开后是那条诊断的四要素:位置、原文、含义、怎么改;某项未能核实时说明这意味着转复核。
4. **完成**:点"确认发布 / 提交复核"才调 `publish` 真正入库。可疑时给出复核单链接,作者可以跟踪。危险时不渲染发布按钮,只能返回修改。

展示用 EDS 组件承载:结论用 `notification` 的三色描边,检查结果用 EDS 严重度 `pill`(未能核实用 `severity-indeterminate`),证据按项折叠。组件内不写死颜色,暗色模式跟随平台;不打分;界面不出现 OWASP/CWE 编号。

接口契约:`evaluate` 与 `publish` 返回同一个报告结构 `{ state, reference, checks[] }`,`checks[]` 为
`{ id, label, description, status, severity, note, findings[] }`,finding 直接承载扫描器的字段:
`{ rule_id, category, aitech, severity, file, line, snippet, title, description, remediation, analyzer }`。
检查项集合、严重度归并、面向用户的检查项名称都由后端提供,前端只渲染——**分类是策略,不在客户端复制一份**;
遇到没有展示映射的类别时显示扫描器自己的 `title`。

### 局限
以下几条是方案本身的边界,不是待办事项。
- 静态扫描可被蓄意规避:自解压打包、"扫描时正常、事后改坏"的可变外链——这是结构性盲区,只能拦明显的和无意的问题。
- 语义层可能判错:模型**不持有任何工具**(不是"禁掉了执行工具"——它连文件系统都碰不到),但误判和漏判
  仍然可能发生;靠人工复核(MR)兜底,不能根除。
- **打包源码里的新型恶意代码**:这一块**部分关闭了**,但不是靠我们。曾经的写法是"判定器不读代码文件,
  没有关闭";而扫描器的语义分析器本来就读代码,并自带一份"声明与实现是否一致"的 SOP(近千行,专门查
  "描述温和、实现恶意"的供应链手法),behavioral 还做 AST 与污点跟踪。剩下的缺口是**读不了的可执行文件**
  (`.pyz`、`.exe`、编码不可解的脚本),它们一律转复核;以及模式与语义都识别不出的新手法。对症的手段是
  运行时权限约束、可信来源(SSO 身份)与事后撤回,均不属本维度。
- 上传者身份由前端自填、未经验证(SSO 未批,属外部依赖):换一个 EID 就是"新用户",来源不可信。所以门禁只看内容、不看是谁传的;要真正锁住身份得靠 SSO 鉴权,不在本轮范围。
- 没有发现不等于没有问题:标注集仍然小,准确率和召回需要更大的样本持续评估。
- **一次完整审计约 80 秒,这是完整流水线的地板。** 拆开量:确定性层约 5 秒;语义层一次调用
  35–49 秒;仲裁一次调用 23–34 秒。每次扫描只有这两次模型调用,输入分别是十几万到二十几万字符,输出
  3–8K。换模型省不了:`claude-sonnet-5` 82.3s、`claude-haiku-4.5` 83.6s、`auto` 79.1s 三者一致;
  降 effort 反而更慢(191.6s)。能省的只有缩小输入(等于少看)或不跑仲裁(误报回来)。

  管道能承受:`location /api/` 是 `proxy_read_timeout 300s`,前端没有自己的 fetch 超时;判定结果按内容
  哈希缓存 600 秒,所以 evaluate → publish 只付一次。**但编辑路径(`PUT /api/skills/{id}`)同步跑审计,
  意味着保存一次改动要等 80 秒**——保存不该是这个量级,这一条待定。

- **`--use-behavioral` 另有代价,给预算。** 一个 26 文件的包开 behavioral 是 29.3 秒且命中数不变;
  一个 10 文件的包是 227.6 秒,多出一条真发现(`BEHAVIOR_EVAL_SUBPROCESS`,eval/exec 与 subprocess
  同处一个脚本)。与文件数无关,是个别大文件让污点分析发散。做法:快分析器总是跑,behavioral 给预算,
  跑不完按"这一层未核实"转复核。

- **模型名必须校验。** `kiro-cli chat --model <不存在的名字>` 会报错并列出可用模型,但
  **`kiro-cli acp --model <不存在的名字>` 静默接受**。打错一个字就会静默用默认模型,"判定可归因到具体
  模型"随之失效。适配器要在启动时验证模型名并快速失败。可用值:`claude-opus-5`、`claude-sonnet-5`、
  `claude-sonnet-4.6/4.5/4`、`claude-opus-4.8/4.7/4.6/4.5`、`claude-haiku-4.5` 等,`auto` 不用。

### 已定的策略口径
- 规则与类别沿用扫描器的规则包,不自建清单;要调轻重就在 `policy.yaml` 里 `severity_overrides`,
  要关噪声就 `disabled_rules`。
- 拒收的门槛不是某个类别名单,而是**两个独立层对同一类别一致且为 critical**(见"结论怎么定")。
- 本轮不收录:功能欺诈(声称做某事、实际返回写死结果并收费,真实语料里 3 例)、反检测规避工具(伪装人类操作、绕过 Cloudflare/reCAPTCHA,1 例)。二者属"行为不当"而非"内容危险",不在本维度范围内。

### 演示态与生产态的差别
同一套代码和 compose,按环境的 `.env` 区分;两个栈在同一台机器上并存,互不影响。

| | 演示(staging) | 生产 |
|---|---|---|
| 数据库 | 本栈自带的 MySQL 容器(`--profile local-db`),数据在命名卷里 | 现有的托管 MySQL |
| 数据 | `python -m app.seed` 生成的分类与示例 skill | 真实数据 |
| skill 仓推送 | 关闭,不建 MR | 开启,需 GitLab token 与评审人 |
| 判定模型 | 与生产相同:钉死 `claude-sonnet-5`(经适配器,由扫描器调用) | 同左 |

数据库必须放在命名卷里,不能放容器内的临时目录,否则重建镜像会清空数据(分类丢了,上传表单的部门下拉就是空的)。上生产只需改 `.env`(指向托管 MySQL、开启推送与 GitLab token、设置评审人),不启用 `local-db` 这个 profile。
