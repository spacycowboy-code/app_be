# 技能仓怎么访问

事实与投影的划分见 [security-compliance.md](security-compliance.md)。这一份只讲一件事:后端**怎么**读写
那个 git 仓库。

## 现在的样子

一棵共享的本地工作副本(`settings.skill_repo_path`,bind mount),五个使用者:

| 谁 | 干什么 |
|---|---|
| `skill_storage.store()` | 写:切分支、写文件、`add`、`commit`、`tag`、`push` |
| `skills.py` `_read_skill_md` | 读 SKILL.md(编辑与审计的输入) |
| `skills.py` 下载接口 | 读整个技能目录打 zip 给用户 |
| `official_import` | 读 `official/`,但为了读到最新会 `fetch` + `merge --ff-only`,失败则 `checkout origin/main -- official/` |
| `export_skills.py` | 一次性命令行工具,写 + 提交 + 推送 |

## 问题不是"缺事务",是把一棵共享可变工作树当成了 API

**最严重的一条:审计闸门可以被绕过。** 可疑内容走 `checkout -B <复核分支>`;在这个窗口里,另一个并发的
正常发布调用 `push HEAD:main` —— 而此时 HEAD 在复核分支上,**未经复核的内容就上了 live**。

其余四条:

* `add -A -- <路径>` 有范围,紧随其后的 `commit -m` 没有 pathspec,提交的是整个索引 —— 别人刚 stage
  的文件会被卷进这次提交。
* `checkout -f main` 会丢掉另一个请求刚写下、还没提交的文件;`official_import` 的 `merge --ff-only`
  会在别人写到一半时挪动 HEAD。
* **push 失败不抛异常**,只返回 `pushed=False`,数据库照常提交 → 市场里看得到、从 GitLab 下载 404。
  这是最可能发生的一条,取决于网络。
* git 提交成功、数据库事务失败 → 仓库里有内容、数据库没有行,而**收敛器只遍历数据库的行,永远补不回来**。

另外版本号来源是反的:从**数据库**读上一版加一,然后写进 manifest、打 tag。两个并发发布会算出同一个
版本号,而 tag 冲突时代码是默默跳过 —— 两份不同内容共用一个版本号,没人知道。

## 抽象

**技能仓只通过 GitLab 访问;本地的任何副本都只是可以随时丢掉的缓存,按 commit sha 寻址。**

这句话同时管住读和写,并且解释了为什么允许有本地缓存:缓存能重算,所以它是投影,不是事实 —— 与
数据库同一条规矩。它**删除**了"两个进程抢一棵工作树"这个问题,而不是用锁去管理它。

## 写

一次原子提交(`POST /projects/:id/repository/commits`),一个技能这一版的全部文件放在同一批 `actions`
里,该删的旧附件也放同一批。

* 每个**已存在**的文件带上 `last_commit_id`。不带就是静默覆盖。
* **冲突返回 409 给调用方,不重试。** 因为每个技能的文件路径是自己的,`last_commit_id` 冲突只可能
  意味着同一个技能被别人同时改了;重试会用自己这份把对方的修改覆盖掉。只有网络错误和 5xx 才重试。
* **内容哈希做幂等**:写之前比对 manifest 里记的哈希,一样就跳过并返回现有版本与 sha。接口本身不幂等
  (相同内容也会产生一个空提交),没有这道闸,客户端重试一次就多涨一个版本号。这道哈希同时满足审计
  文档要求的"内容指纹",能证明上架的就是被审计的那份。
* 可疑内容:建复核分支 + 首次提交是同一个请求(`start_branch`),然后开 Draft MR。分支名带审计 ref,
  所以不会互相撞。**没有本地工作树,所以上面那个闸门绕过的洞是被结构消除的,不是靠加锁躲开的。**
* 版本号从**仓库**里那份 manifest 推,不从数据库加一。

## 读

单文件 `files/:path/raw`、列目录 `repository/tree`、子目录归档 `repository/archive.tar.gz?path=`,
全部带 `sha`。

* 缓存键是(路径, commit sha)。放**容器本地**目录 —— 不能是 bind mount,否则又把副本钉回一台机器。
  要有大小上限,并记命中率:没有命中率数据,缓存悄悄失效了没人会发现。
* **读失败不要回落到数据库里的 `instructions`。** 那是第二份事实,回落等于拿旧内容去审计或编辑。

## 读路径:为什么不是"每次从 GitLab 取"

上面那套读法(按 sha 走接口 + 本地缓存)解决了共享可变工作树的问题,但它把 GitLab 放在了**每次下载的
路径上**。注册中心不这么做:

| 项目 | 读路径 |
|---|---|
| npm / PyPI / crates.io | 发布时把**不可变产物**放进对象存储,下载从那里走;git 不在读路径上 |
| Backstage | git 是真相,但**摄取**进自己的库,服务时读自己的库 —— 官方文档原话是目录 "should not be considered the ultimate source of truth, instead... a caching mechanism" |
| Homebrew | formulae 在 git,`formulae.brew.sh` 的 JSON 由定时任务从默认分支**生成**;生成物里带 `tap_git_head`,记着自己来自哪个 commit |
| cargo | 索引由**注册中心**提供。原来的做法是让客户端克隆一个 git 索引仓库,RFC 2789 因为不 scale 改成按 HTTPS 逐文件取 |

共同点:**git 是创作与复核的地方,不是运行时读路径。发布时摄取一次,之后服务只读自己的产物。**

所以终态是三块,而不是两块:

1. **git** —— 创作 + 复核。MR 是复核机制,这一点不变
2. **产物存储** —— 合入时摄取一次,把那一版的不可变包放进去(digest 寻址)。下载从这里走
3. **数据库** —— 索引 + 门户事实。存产物的 digest 与元数据,**不存内容正文**

按这个模型,`rp_ai_skill.instructions`(22 行非空,存的是 SKILL.md 正文)是把内容复制进了索引,不该长期
保留;而"按 sha 读"的客户端位置也变了 —— 它不是给请求路径用的,是**给摄取用的**。

### 为什么先不做

需要先定三件事,而它们都不在这个仓的控制范围内:

* **能不能在 Artifactory 建一个通用仓库**(权限在别人手上)。已有的 OCI 注册中心也能存任意产物(ORAS),
  但同样要先确认权限与保留策略。
* **合入触发摄取用什么** —— GitLab webhook,还是技能仓自己的 CI。
* **摄取失败的语义**:MR 已经合了、产物没进去,这个技能算不算已发布?这又是一次双写(见下),需要
  一条明确的恢复路径,而不是靠人发现。

在这三件定下来之前,"每次按 sha 读 + 缓存"是可用的过渡:它消除了共享可变状态(那是正确性问题),
只是没有消除对 GitLab 的运行时依赖(那是可用性问题)。两者的紧迫程度不同。

## 双写这件事要叫出名字

"先提交 GitLab,再写数据库"是**双写**(dual write):两个存储各写一次,不可能原子。中间失败会留下
"仓库有内容、数据库没有行"。业界对这个问题的处理是:**指定一个真相,其余由它派生**(事件溯源、
transactional outbox),而不是想办法把两次写变成原子的。

我们这里的形状是:**git 是内容的真相,数据库那行由摄取产生**。所以:

* 顺序永远是先 git 后数据库 —— 反过来那种失败("数据库有、仓库没有")无法从事实恢复
* 收敛器不是"补一补"的杂活,它是**摄取的重放**,是这个模型里必需的一环
* 摄取必须能对任意 commit 重放,而不只是对"刚刚那一次"

## 分层的实际情况

改这件事会动哪些层,先记清楚现状:

* `app/routers/` 15 个文件 —— HTTP 入口,同时**直接查数据库**(10 处)、**直接读写文件**
  (`skills.py:55` 拼路径读 SKILL.md,`skills.py:316` 遍历目录打 zip)
* `app/services/` 14 个文件 —— 领域操作
* `app/models/` 干净,没有业务逻辑;需要的列已经有了(`repo_commit` 22/22 非空、
  `rp_ai_skill_version.commit_sha` 27/27 非空)
* **没有 dao / repository 层**

所以"内容访问"这个边界**今天不存在**,这次改动是把它建起来,必然要动路由层。

顺带记一笔、但**不要一起做**:数据库查询散在路由里是既有的分层问题,它只影响整洁,不产生错误结果;
和内容访问混在一个改动里会让 diff 无法评审。

## 数据库是投影

* 顺序固定:**先提交 GitLab,再写数据库**。反过来永不做 —— "数据库有、仓库没有"无法从事实恢复。
* 收敛器加一步:列出 **live 分支**上的 manifest,数据库缺行就补、版本落后就更新。只认 live 分支,
  复核分支上的内容按定义还没上线。
* 字段分工**复用 `official_import` 已有的那套**,不要另立一套:manifest 拥有的字段照抄,运行时字段
  (`rating` / `downloads` / `review_count` / `is_trending`)保留不动。

## 实测过的接口行为

在真实仓库上验的(探测分支已删,`main` 未被触碰):

| 试的什么 | 结果 |
|---|---|
| 一次提交多个文件 + 二进制 | 成立,1MB 回读字节一致 |
| 体积 | 30MB 原始文件(请求体 40MB)也过,12 秒。当前最大附件 9.3MB |
| 一次提交里混 create + delete | 成立 |
| `update` 带正确 `last_commit_id` | 201 |
| `update` 带过期 `last_commit_id` | **400 `The file has changed since you started editing it`** |
| `update` 不带 `last_commit_id` | 201,**静默覆盖** |
| `start_sha` | 只用于建分支;分支已存在时报 "branch already exists"。**不是并发保护** |
| 内容完全相同的 `update` | 201,**产生一个空提交**(所以接口不幂等) |
| `create` 已存在 / `update` 不存在 | 各自 400,所以要先知道文件在不在 |
| 子目录归档(9.1MB) | 2.1 秒 |
| 列目录 / 单文件 raw | 各 0.5 秒 |

### 读路径:动手前量过的两件事(2026-08-20,生产数据 + 技能仓 139337)

**一、回落分支可以直接删,不是数据迁移。**

生产 22 个技能:`storage_path` 为 NULL 的 **0** 个、为空串的 **0** 个;缺 `repo_commit` 的 **0** 个。
所以 `_read_skill_md` 里"读不到就回落到 `instructions`"这个分支,**对现存数据一个都不生效**,删掉不需要
迁移。`instructions` 22 行非空(最长 32987 字符)照旧留着,但它是缓存,不是回落对象。

**二、归档取回 + 转 zip 的代价(22 个技能全量测,22/22 成功)。**

| | 结果 |
|---|---|
| 最大技能 | 9315K tar.gz → 9316K zip,只有 3 个文件(一个大附件) |
| 取回耗时 | 中位约 0.8 秒,平均 1.64 秒,**最慢 10.84 秒** |
| 同一个归档紧接着再取 | **2.08 秒** —— 说明 GitLab 是**按需生成**归档,首次那 10.84 秒是生成成本 |
| tar.gz → zip | 最慢 **0.30 秒**,峰值内存 **32MB**(最大那个技能) |

由此定下三件:

* **对外仍然给 zip**,契约不变。转换只要 0.3 秒,没有理由让用户那边跟着改。
* **内存不是问题**:峰值 32MB,测试环境后端限额 2G,生产没设限额(当前实际用 187MiB)。
  转换是整块进内存(tar 和 zip 各一份),在这个数据量下不值得改成流式。
* **首次下载会变慢,要认这笔账。** 今天是从本地磁盘读,几乎瞬时;改完首次要 0.6–11 秒。
  按 sha 缓存能吃掉重复的部分 —— 同一个版本只有第一次付这个钱,而下载量是每天 9 次。
  **接口的超时预算要按 11 秒设,不是按 2 秒**;缓存命中率必须有数,否则悄悄失效了没人发现。

## 放弃了什么

* **可移植性**。这套绑在 GitLab 的接口上。GitOps 工具(如 Flux 的镜像自动更新)坚持 clone+push 就是
  为了支持任意 git 服务器。我们长期在 GitLab 上,所以接受这个绑定 —— 但这是这个选择唯一实质的代价。
* **读也依赖 GitLab 可达**。今天 GitLab 挂了还能本地提交、稍后再推,但那正是 `pushed=False` 静默分叉
  的来源。这是拿"悄悄不一致"换"明确失败"。
* **下载首次变慢**(最大的技能 2.1 秒),缓存之后只有第一次。

## 两处定下来的规矩

**删除语义:仓库里没了 → 收敛器把 `status` 置成 `archived`,不删数据库行。**

那一行还带着 git 里没有、也算不出来的门户事实:下载量、收藏、评价、审计记录。为了镜像一次仓库删除去
销毁它们,是把"数据库是投影"这条规矩用反了方向——投影的意思是**派生字段**能重算,不是**门户自己的
事实**可以丢。

可见性跟着仓库走:公开列表按 `status == "approved"` 过滤(`app/routers/skills.py:154`),所以置成
`archived` 之后它自然从列表里消失,前端不用改。`status` 是 `String(16)`,放得下。写入者仍然只有收敛器
(与"复核结果只经 reconcile 落地"一致)。`official_import` 现在写的"从不删除"是这条的一个特例。

**token:用项目访问令牌(Maintainer),不用任何人的个人令牌。**

三个理由:

* `main` 是保护分支,实测只允许 **Maintainer(access_level 40)** 推送,Developer(30)会被拒 ——
  所以"给一个 Developer 的专用 token"这条路走不通。
* 今天服务用的是**一个同事的个人 token**。后果:服务替用户开的每个 MR 都显示成她;她一旦轮换或离开,
  服务就断。
* 项目访问令牌有独立的 bot 身份,归属清楚,轮换不牵连任何人的账号。

审计引擎只读技能仓,另发一个只读的,不要复用写权限那个。**已发**:技能仓
(`rp-ai/rp-ai-skill`)的项目访问令牌 `skill-audit-engine-read`,scope 只有 `read_api` +
`read_repository`,权限级别 Reporter,到期 2027-08-19。它配在引擎的环境里(测试环境的
`SKILL_AUDIT_TEST_ENV`),读仓的代码是新仓的 `skill_audit/skill_repo.py`。

## 时机

等重复性维度的阶段性验收做完再动。这件事会同时改到路由、服务两层和内容读写路径,与正在进行的功能开发
在同一批文件上冲突。

## 落地顺序

每步都能单独回退。

0. **两行止血,不等重构**:`commit -m msg -- <路径>` 加上 pathspec;push 用明确分支名
   (`refs/heads/main:main` / `<复核分支>:<复核分支>`)而不是 `HEAD:`。今天就消除闸门绕过。
1. **先切读**:下载、`_read_skill_md`、`official_import` 改走接口 + 缓存。风险最低,先把"本地只是缓存"
   这条规矩立起来。
2. **再切写**:发布器取代 `skill_storage`。
3. **删干净**:两个挂载(技能仓、ssh 私钥)、`skill_repo_*` 配置、`SkillStorage`。
4. 收敛器加 manifest 补齐。

做完第 3 步,`audit-backend` 就没有本地状态了,可以在任意一台机器上起来 —— 这才是这次重构的目的,
不是抗并发。发布器**是模块不是独立服务**:一天两次上传,独立服务只在需要串行化或独立扩容时才划得来,
而这次改完连串行化都不需要了。
