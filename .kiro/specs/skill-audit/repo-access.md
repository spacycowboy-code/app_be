# 技能仓怎么访问

后端怎么读写技能内容。哪些字段算事实、哪些算投影,见 [security-compliance.md](security-compliance.md)。

## 要做成什么样

门户不保存可以被改动的内容副本。读内容必须给一个不会变的引用;发布是一次带前置条件的写,成功后返回新的
引用。

git 是这个内容存储现在的实现,同时也是复核用的工作流;引用现在是 commit sha。抽象里不写 GitLab,是因为
一写进去,接口就会带上 project id、`last_commit_id` 这些只有 GitLab 才有的概念,调用方也跟着知道它们;
以后要换存储,改的就不止这一层,调用方也得跟着改。

```
read(ref, path)             -> bytes          # read_text 是文本版
list_files(ref, prefix)     -> [path]
read_tree(ref, prefix)      -> {相对路径: 字节}
head_ref(branch)            -> ref            # 这个分支现在是哪一版
version_of(prefix, at=ref)  -> ref            # 这个技能内容的标识
publish(files, expect=ref)  -> ref            # expect 对不上就报冲突
```

三个设计选择,理由都是实测的:

**`read_tree` 交出的是路径到字节的映射,不是归档字节。** 归档里套着两层目录(GitLab 自己的
`<项目>-<ref>-<ref>-<路径>/`,再加技能在仓库里的完整路径)。剥这两层是存储细节,调用方不该知道。
格式用 `archive.zip`,因为门户的市场下载已经在用它,没必要再引入 tar.gz。

**`version_of` 返回的是这个技能内容的标识,不是某一次提交。** 调用方需要的是"只有这个技能自己变了才会
变的值"。要是用整个仓库的 head 当这个值,别人改任何一个技能都会让所有技能显示成有更新。git 用"最后改过
这个路径的提交"来回答,产物存储会用包的 digest 回答,所以调用方只能拿它比较,不能解析。

**`publish` 一次只切换一个 manifest 或指针,不承诺"同时写 N 个文件"。** git 顺手给了多文件原子性,但
对象存储没有跨对象事务(S3 的 `If-Match`、GCS 的 `ifGenerationMatch` 都只管一个对象)。要是抽象依赖 git
这项额外能力,以后换存储就得重新设计。

后端因此没有本地状态:不挂技能仓的工作副本、不挂 ssh 私钥,可以在任意机器上起来,也能多副本。
这是这套抽象最主要的收益 —— 只要那两个挂载还在,后端就绑死在一台机器上,生产也上不了集群。
并发不是动机:一天两次上传,不需要排队。

## 哪个字段听谁的

* 内容听 git 的,因为需要历史、diff 和复核
* 下载量、收藏、评价、审计记录、用户听数据库的,git 里算不出来
* 上架状态谁都不听,它是算出来的:看复核 MR 合没合

判断办法:能从别处算出来的就是投影,算不出来的才是事实。每个投影都要有一条真能跑起来的重算路径,否则它
会慢慢变成第二份事实。`rp_ai_skill.instructions`(22 行非空)按这条算是缓存,读不到内容时不能拿它顶替。

## 写

一次提交(`POST /projects/:id/repository/commits`)把这个技能这一版的所有文件、以及要删掉的旧附件放在
同一批动作里。

* 已经存在的文件必须带 `last_commit_id`。不带的话 GitLab 会直接覆盖,不报错。
* 冲突返回 409,不重试。每个技能有自己的目录,冲突只可能是同一个技能被两个人同时改;重试会用这次的内容
  覆盖掉对方刚写的。只有网络错误和 5xx 才重试。
* 内容没变就不提交。接口本身不去重,同样的内容也会产生一个空提交,客户端重试一次版本号就白涨一格。所以
  写之前先比内容哈希。这个哈希也是审计要的内容指纹,用来证明上架的就是被审计过的那一份。

  这道闸原来够不到:`store()` 每次都往 manifest 里塞一个新的 `storedAt` 时间戳,内容永远不同,闸永远
  不触发。按"每个字段听谁的"这条判据,"我们什么时候存的"是门户事实,不该写在内容里。`storedAt` 已删除
  (!59),闸现在生效,有一条测试断言 manifest 里不含它。另外闸只比作者可见的内容、不含 manifest 本身 ——
  版本号是先算好写进 manifest 的,连 manifest 一起比的话内容又会永远不同。
* 可疑内容:建复核分支和第一次提交是同一个请求(`start_branch`),然后开一个 Draft MR。分支名带审计
  编号,不会互相撞。
* 版本号从仓库里的 manifest 推,不从数据库加一。两个并发上传从数据库加一会算出同一个版本号,而 tag 撞了
  的时候代码是不报错跳过的——两份不同的内容共用一个版本号,没人会发现。

## 读

单文件用 `files/:path/raw`,列目录用 `repository/tree`,取整个技能目录用 `repository/archive.zip?path=`,
都要带引用。

* 缓存按(路径, 引用)存。放容器本地目录,不能用 bind mount,否则又把内容绑回一台机器。要设大小上限,
  并且要记命中率——没有命中率,缓存哪天失效了没人会知道。
* 读不到内容时不要改用 `instructions` 那一列。那是同一份正文的另一个副本,顶替之后拿去编辑或审计的可能
  是旧内容,而从结果上看不出来。
* 给用户的仍然是 zip,接口不变。
* 超时按 11 秒算。GitLab 的归档是现做的,最大那个技能第一次要 10.84 秒,紧接着再取只要 2.08 秒。

## 现在不做产物存储

npm、PyPI、crates.io 都是在发布时把不可变的包放进对象存储,下载不经过 git;Backstage 把 git 的内容摄取
进自己的库,再从自己的库对外服务。这么做主要是为了读的量和可用性,不是为了不可变——git 本身就是内容
寻址的,sha 就是 digest,27 个版本的 sha 都已经记着。

现在读的量是每天 9 次下载(总共 87 条记录,最近 7 天 62 条)。这个量级下,按引用读加本地缓存就够用,
不是临时凑合。下面任何一条成立再做,那时候是换实现,不用重写:

* 下载必须在 GitLab 不可用的时候也能用
* 读的量涨到 GitLab 开始限流
* 已发布的包需要比仓库活得更久(现在的规矩是仓库删了把 `status` 置成 `archived`,不删行)

真要做,先得解决三件不在这个仓库里的事:Artifactory 通用仓库的权限、合入之后靠什么触发摄取(webhook
还是 CI)、以及 MR 合了但摄取失败时这个技能算不算已发布——最后这件又是一次双写。

## 数据库里的行怎么来

* 顺序固定:先提交 git,再写数据库。反过来会留下"数据库有、仓库没有",而这种状态没法从内容恢复。
* 这条规矩只管**内容的投影**(技能那一行),不管数据库自己拥有的事实。审计记录是事实:它记录"审计跑过、
  结论是什么"。现在的代码把它放在写内容之后(`upload.py` 先 `store()` 再 `gate.record`,最后一次
  `db.commit()`),所以写失败的时候这条记录整个丢掉 —— 跑了 40 秒的审计没有痕迹,健康端点的失败率也少
  算一次。被拒的内容那条路反而是先记后提交。应该统一成:先把审计记录落库,再写内容。
* 先 git 后数据库这两步不可能原子,中间失败会留下"仓库有、数据库没有"。所以数据库那一行必须能从 git
  重新算出来:收敛器列出 live 分支上的所有 manifest,缺行补上、版本落后就更新。它必须能对任意一个
  commit 重算,不能只处理刚刚那一次。
* 字段分工照 `official_import` 已有的那套:manifest 里有的字段照抄,`rating`、`downloads`、
  `review_count`、`is_trending` 这些运行时字段不动。

## 仓库里现在有两条写 GitLab 的路径

这一份讲的是**技能内容**:一个共享仓库、多人并发编辑、内容要过复核闸门。所以用 Commits API 加前置条件。

`app/services/gitlab_projects.py`(agent 上传)走的是另一条:`git push` 加子进程,推的是**每个 agent
一个新建的项目**。它的注释写了理由 —— 50MB 的包走 Commits API 要 base64,请求体会炸。这不与上面矛盾:
它没有共享可变状态(每次一个新项目)、没有并发编辑同一份内容的问题,也不经过技能的复核闸门。

选哪条的判据:**改的是共享仓库里已有的内容,用 Commits API;第一次把一整个包放进一个专属的新项目,
用 push。** 不要在技能这条路上引入 push,也不要为了统一把 agent 那条改成 base64。

## 放在哪一层

新模块放 `app/repositories/`,职责是回答"字节在哪",和 dao 一个意思。以后把数据库查询也搬进这一层,
是同一个模式,不是另立一套。

现在的分层情况:`app/routers/` 既处理 HTTP 又直接访问数据(10 处直接查库、2 处直接读文件),
`app/services/` 是业务逻辑,`app/models/` 只有表定义,没有 dao 层。所以"内容访问"这个边界现在不存在,
建起来必然要改路由层。

数据库查询散在路由里这件事单独处理,不和这次混在一个改动里:它只影响代码整洁,不会产生错误结果。

## 删除

两个方向都定了,只定一个方向会在收敛器补齐 manifest 的那天出事。

**仓库里删掉一个技能** → 收敛器把 `status` 置成 `archived`,不删数据库那一行。

那一行上还有 git 里算不出来的东西:下载量、收藏、评价、审计记录。为了跟仓库保持一致就把它们销毁,是把
规矩用反了 —— 投影的意思是派生字段可以重算,不是门户自己的记录可以丢。

公开列表按 `status == "approved"` 过滤,所以置成 `archived` 之后它自然从列表消失,前端不用改。
这一列的写入者只有收敛器。

**门户上删掉一个技能** → `delete_skill` 用 `publish(files={})` 把内容从仓库移掉,数据库那一行置成
`archived` 保留门户事实。所以门户上的"删除"实际是下架:市场里看不到,门户自己的记录还在,
而且收敛器不会把它扫回来 —— manifest 已经不在仓库里了。

不提供把数据库那一行真删掉的接口,理由同上。

`delete_skill` 的鉴权是 `acting_eid(request, x_user_eid)`,只有**上传者本人或 `audit_admin_eid`**
能下架,其他人 403。

## token

**具体发了哪些令牌、配在哪、到期、谁能轮换,在 platform-ci 的 `CREDENTIALS.md` 里,不在这份文档。**
令牌清单只在一处维护,避免两份清单不一致。这里只写当时为什么这么选。

用项目访问令牌,不用某个人的令牌。GitLab 创建项目访问令牌时会同时建一个 bot 用户,这就是它给的服务
账号机制,可以限 scope、设到期。个人令牌在官方文档里的定位是"代表某个人的工具"(IDE、glab 之类);
CI 场景推荐用 job token,但我们是常驻服务,不适用。

改造之前服务用的是一位同事的个人令牌:服务开的每个 MR 都记在那个人名下,而那个人轮换令牌或者离开,
服务就断。
现在两个环境都是项目访问令牌。

最小权限落在三件事上,都不增加流程:

* 令牌只对技能仓这一个项目有效
* 每个环境一个,测试环境用测试仓 `rp-ai-miao/rp-ai-skill-test`
* 有到期时间,到期即失效,不靠人记得撤

**scope 必须是 `api`,不能是 `write_repository`。** 后者只对 git push 有效,用它调 Commits API 会得到
403 insufficient_scope。

**角色只要 Developer,不需要 Maintainer。** `main` 是保护分支,但"Developer + 在保护分支的推送白名单里"
就能推 protected main —— 实测:不在白名单时直接推是 403,加进白名单后同样的令牌 201。生产现在用的
`portal-skill-repo-prod` 就是 Developer。

合并权限仍然只给 Maintainers,服务身份不在里面:服务能提议,不能自己批准。

考虑过"服务永不写 live,只推复核分支再由 CI 自动合"这个形状,结论是不做:闸门本身跑在门户进程里,门户
被打穿的话攻击者把内容标成 `pass`,CI 照样合——保护是假的,而代价是多一条流水线、多一个凭据、多一次
"MR 合了但没生效"的双写。要真降这个风险得把判定移出门户(引擎签名、合并策略验签),那是另一个量级的
改动,现在的规模不值当。

吊销一个令牌**不会**把它从保护分支白名单里摘掉,要单独摘。改造时那个旧的 `skill-sync` 身份
(就是原来挂进容器的那把 ssh 私钥)已经吊销、部署密钥已删、白名单条目已摘除。

## 实测过的接口行为

都在真实仓库上验过,探测分支已删,`main` 没被碰过。

| 试的什么 | 结果 |
|---|---|
| 一次提交多个文件 + 二进制 | 成功,1MB 回读一致 |
| 30MB 原始文件(请求体 40MB) | 成功,12 秒 |
| 一次提交里混 create 和 delete | 成功 |
| `update` 带正确的 `last_commit_id` | 201 |
| `update` 带过期的 `last_commit_id` | 400 `The file has changed since you started editing it` |
| `last_commit_id` 跟什么比 | 跟这个文件比,不跟分支比:它问的是"这个文件在这个提交之后被改过吗"。文件自己的最后提交、当前分支头都能通过;别人改了别的文件把分支头推走,不会造成冲突(三次对照实测)。所以一次写只用一个 `expect` 引用就够,不必逐个文件查最后提交;也因此"冲突只可能是同一个技能被并发改"成立,409 不重试是对的 |
| `update` 不带 `last_commit_id` | 201,直接覆盖,不报错 |
| 内容完全一样的 `update` | 201,产生一个空提交 |
| `start_sha` | 只在建分支时有用,分支已存在会报 "branch already exists",不是并发保护 |
| `create` 已存在的文件 / `update` 不存在的文件 | 各自 400,所以写之前要知道文件在不在 |
| 列目录 / 单文件 raw | 各 0.5 秒 |

`archive.zip?path=` 与转 zip 的开销,22 个技能全量测过(2026-08-20,22/22 成功):

| | 结果 |
|---|---|
| 最大的技能 | 9317K,3 个文件 |
| 取回耗时 | 中位 0.8 秒,平均 1.64 秒,最慢 10.84 秒;同一个归档再取 2.08 秒 |
| 转 zip | 最慢 0.30 秒,峰值内存 32MB(后端限额 2G,实际用 187MiB) |

生产 22 个技能的 `storage_path` 和 `repo_commit` 都有值,`rp_ai_skill_version.commit_sha` 27 条也都有
值。所以删掉"读不到就用 `instructions`"这条回落不需要迁移数据。代价是第一次下载从本地磁盘的几乎瞬时
变成 0.6–11 秒。

`publish` 也在真实仓库上验过:新目录加切分支、相同内容不产生提交、改删增一次提交完成、用过期引用写报
冲突、`files={}` 把目录清空。探测分支已删。

## 代价

* 只能用在 GitLab 上。所有读写都走它的接口,以后要换 git 服务,这一层得重写。我们长期在 GitLab 上,
  接受这一点。
* GitLab 挂了,上传和编辑会直接报错说没保存。以前不报错:它会先写本地再推送,推不上去就只写了数据库,
  于是市场里看得到这个技能,点下载 404,而页面显示"已保存"。所以以前那个"还能用"是假的。
* 看内容和下载也要连 GitLab。以前从本地磁盘读,GitLab 挂了也能下载。现在第一次读要 0.6–11 秒,之后走
  缓存;GitLab 挂了,没缓存过的技能下不了。

第 2 步让三处调用方的语义变了,读代码时注意:

* `pushed` 恒为真。以前本地提交能成而推送能败,所以会返回 `synced=False` 加一句"改动已保存,但同步到
  GitLab 失败"。现在没有本地提交,调用成功就意味着内容在 GitLab 上;字段留着是因为前端在读。
* 写失败让请求失败,不再先写数据库再警告。
* 版本号从仓库的 manifest 推,不再从数据库加一。

生产验收(镜像 `26349bab`):按引用读到三个技能的正文;写入 v1.0.0;同内容再写版本与引用都没动;
真改动得到 v1.1.0;下架后内容从仓库移掉。去掉挂载之后再验一遍:工作副本路径与 `/root/.ssh` 都不存在,
读写照常。

### 还剩的那一步:收敛器补 manifest 扫描

必须排在第 3 步之后,否则它会把删掉的技能扫回来 —— 第 3 步已完成,所以这一步现在可以做了。

同时要兜住另一条投影的重算路径:"复核 MR 存在"这件事现在只在写入时建立,如果开 MR 那一步失败,
技能会停在 pending 而没有 `mr_url`。收敛器应当扫出这种技能并重新处理。相关改动见 !65 —— 开不出 MR
现在会删掉复核分支并返回 503,不再静默留下一个没有 MR 的分支。

## 每个环境都要有能写技能仓的令牌

切写之后没有"先写本地"这条路,写不成就是写不成。令牌没配好,上传和编辑全部返回 503。

两个环境都已经配好项目访问令牌:生产 `portal-skill-repo-prod`、测试 `portal-skill-repo-test-dev`,
都是 `api` scope + Developer + 在对应仓 main 的推送白名单里。生产原来用的是一位同事的个人令牌,
已经换掉。到期时间与轮换方式见 platform-ci 的 `CREDENTIALS.md`。
