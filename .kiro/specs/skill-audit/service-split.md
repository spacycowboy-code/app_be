# 把审计拆成独立服务

事实与投影的划分见 [security-compliance.md](security-compliance.md),重复性维度的模型见
[duplication.md](duplication.md)。这一份讲两件事:边界画在哪,以及跨仓之后的契约是什么。

## 结论

新仓 `skill-audit`(group `rp-ai-miao`)拥有整个审计能力:引擎 + 判定器,产出两个镜像。引擎是无状态
HTTP 服务。`gate.py` 与 `reconcile.py` **留在门户**。

一句话说清分工:

> **引擎给事实和分类,门户负责措辞和决定。**

引擎报"跑了没跑、命中什么、覆盖到什么程度、判定是什么";门户决定要不要写、技能什么状态、怎么讲给
上传者和复核人听。**决定永远不依赖门户侧的派生** —— `state` / `coverage` / `cause` 都是引擎给的值,
门户派生错了最多是显示难看,不会误放行。

## 为什么是服务,不是库

- 第三方扫描器 `cisco-ai-skill-scanner==2.0.12` 现在装在**门户主镜像**里(CI input `extra_pip`)。
  扫描器升一个版本要重建并重新部署门户。
- 判定器早就是独立服务,链路今天已经是 门户 → HTTP → 判定器。再加一跳是同一个形状,不是新概念。
- 扫描是重负载(`audit_scan_timeout` 默认 900 秒),今天和请求服务共进程共内存,一次跑飞的扫描会拖
  住后端 API。
- 库省下的只有那一跳网络,而版本一样要钉、接口改一样要两边升。省不到协调成本。

## 边界

**搬走**:`scan` `scanners` `verdict` `pipeline` `report` `types` `acp`(约 1350 行,**逐文件核过零
`sqlalchemy`、零 `app.models` 引用**)、`skill_audit/policy.yaml`、以及判定器
(`app/acp_openai_service.py`、`Dockerfile.judge`、`.kiro/agents`)。

判定器跟着走,因为它是"模型访问能力",只有审计用;而 `acp.py`(客户端)与判定器(服务端)是同一个
协议的两半,同仓才能原子地改契约。搬完门户仓里既没有扫描器也没有 kiro-cli。

**不搬**:`gate.py`(决定 `status`、写审计记录)、`reconcile.py`(从 MR 状态重算投影)。它们讲的是
门户怎么处理审计结论,不是怎么审计,而且是唯一碰数据库的两个文件。

**引擎不碰技能仓的工作副本** —— 搬走的那些文件对 `skill_repo_path` 零引用,所以引擎从第一天就是无
状态的,不需要先做别的改造。

## 分类归引擎,措辞归门户

这条线是这次拆分最容易留债务的地方,所以单列。判定标准很好用:**引擎的响应里出现中文展示文案就是
味道不对**(`reason` 与 `remediation` 除外 —— 那是内容,不是界面文字)。

| 归引擎 | 归门户 |
|---|---|
| 一条发现属于哪个 category、多严重 | 这个 category 叫什么、按什么顺序读 |
| 覆盖度 `complete/partial/none`、原因 `scanner_timeout/…` | 这些值怎么讲给作者和复核人听 |
| 缺口归属 `author/platform/shared` | 渲染成"作者"/"平台" |
| `remediation`(要改什么)、`reason`(判定理由) | 谁上传的、要不要写、技能什么状态、去重键 |

早先的版本把"按 category 归并成 checks"放在引擎并随响应下发,已经撤回。撤回的原因是实测出来的,不是
风格偏好:

- **同一条 finding 在一个响应里出现两次,而且两份不一致。** 顶层 `findings[0].remediation` 是 `None`,
  嵌在 checks 里那份有值 —— 归并顺手补了处置建议,而顶层那份已经序列化过了。调用方存哪一份都是赌运气。
- **常量重名。** 那张顺序表叫 `KNOWN_CATEGORIES`,而这个名字在 `verdict.py` 里已经有主:一个 frozenset,
  参与严重度判定,还有测试强制升级扫描器时必须分类新类别。同包同名,一个管决定一个管顺序。
- 归并所需的东西**门户本来就有**:findings 带 `category`,结论带顶层 `incomplete`。

处置建议在**结论装配处**补齐,不在渲染处。门户是"先写审计记录、后建报告"的顺序,在渲染处补会让库里
存的 finding 没有处置建议、而复核人看到的那份有 —— 门户今天就是这个样子,拆分时一并修掉。

## 接口

```
POST /v1/audits        → stage 事件…(每 15 秒一个 ping)…最后一个 result 或 error
GET  /v1/vocabulary    → {causeOwners}:cause -> author|platform|shared
GET  /health           → 只证明进程活着
```

**只有事件流一种表述。** 曾经还有一条"`Accept: application/json` 同步返回结论"给发布路径用,删掉了:
它**没有保活**。引擎连上了但不出声(挂死)时,调用方只能等满读超时,而读超时必须大于一次审计的最坏
情况。事件流有 ping,读超时可以压到一分钟。客户端解析事件流的代码本来就要写,那条表述省不下什么,
只多一个没人调用的接口。

**不做"POST 拿任务号,再 GET 查状态"**:那样服务要记住任务状态,而两次请求可能落到不同副本,除非做
粘性路由。一个请求一条连接从头到尾,服务不需要任何任务表,几个副本都能跑。

**`/health` 只证明进程活着**,不检查判定器和扫描器。引擎 healthy 不等于审计链路 healthy;要判断链路,
看每次审计返回的 `coverage` 与 `cause`。

**`error` 事件带机器可读的 `cause`。** `bundle_too_big` 是作者能改的输入问题(门户回 422),
`engine_failed` 是平台的问题(转复核或让人重试)。同一个 cause 的话,上传者只会看到"审计失败",而他
其实只需要把附件改小。

## 契约:开放集合发布成数据,封闭枚举随版本走

跨仓之后门户与引擎进入两个独立的 sha 空间。今天门户和判定器是**同一个 commit**(版本集合里两个 tag
完全相同),兼容性是结构保证的;拆开后只能靠契约。契约由三部分组成:

**一、响应的字段名**。门户保留一份 DTO 镜像(`AuditResult` / `Finding`,含 `is_danger` 这个属性),
不共享包。新增字段兼容,改名或删字段不兼容 —— 那要升 `apiVersion`。

**二、封闭枚举随 `apiVersion` 走**:`state`(pass/suspect/danger)、`coverage`(complete/partial/none)。
它们是响应结构本身的一部分,还落在门户自己的库列里,所以不发表、不缓存;门户校验 `apiVersion`,不匹配
按引擎错误处理,遇到未知值渲染成"未知"而不是猜成最接近的那个。

**三、开放集合由属主发布成数据**:`causeOwners`。cause 会增加,所以它必须从属主这里发出去,而不是让
门户各留一份副本 —— 归属是 cause 的纯函数(`verdict.py` 的原话:"两个可能互相矛盾的字段就是两次犯错
的机会"),副本分散在两个仓里,漂移时没有任何一处会报错。门户缓存它,并在**取不到时说自己算不出来**,
而不是报一个错的数字。

早先这里还打算发 `hygieneRules` 与 `incompleteRules`,给门户算 check 的 `gating` 与状态用。查过消费者
之后删掉了:`gating` 门户只是原样转发、**前端一处都没引用**;而"哪些规则表示某一层没跑完"门户并不
需要 —— 结论里本来就有顶层的 `incomplete`。为没有读者的字段发布一张表,是给两个仓各加一份要维护的
东西。真出现第二个消费者时再加,那时它有明确的读者。

**回滚要成对回**:只回一个仓可能落到不兼容的组合上。

## 门户 → 浏览器:这次要顺手修掉的两处

`checks` 只有一个消费者(上传向导);复核 MR 只用 `findings`。核过前端实际消费的字段之后:

- **`gating` 去掉**。门户只是转发,前端类型里没有声明、代码里零引用。前端没声明的字段删掉不是破坏性
  变更。
- **"未能核实"那一行的状态发 `degraded`,不发 `incomplete`**。前端判的是 `check.status === 'degraded'`
  (两处:严重度色块给 `severity-indeterminate`、标签给 `Not verified`),而后端一直发 `incomplete`,
  于是那一行落到 `else` 分支,被渲染成 **"Finding" + 严重度色块** —— 一个"这一层没跑完、结果未知"的
  行,显示成了一条发现。措辞归门户,所以门户直接发消费者认识的那个词,零前端改动。

**已知缺口,这次不动**:`status=clear` 后端从来不发(只有出现 finding 的 category 才生成 check),而
前端有三处 `clear` 分支。也就是说"看见什么被检查过并且通过了"这件事其实没实现。它是功能缺口,需要单独
决定,不该混进拆分。

## 失败语义:不能一刀切

`gate.py` 里已经有一条精确的规则,拆分**必须保留**:

> `unavailable` = 审计跑不起来 **且** 内容已经上线 → 调用方什么都不要改,让它重试。
> 别处遇到不可用的判定会转人工复核,那是在提交者身上 fail closed;这里那样做,是在**每一个已经在用
> 这个技能的人**身上 fail closed,而它一分钟前还是好的。

所以:

| 情形 | 处理 |
|---|---|
| 引擎不可达 / 版本不匹配 / 审计没跑起来 | 客户端返回 `state=suspect` + `verdict=error` + `cause` |
| 新提交 + error | 转人工复核(与今天进程内扫描器坏掉时一致) |
| **重新发布已上线内容 + error** | **retry,不降级**。不能把线上好技能因为一次抖动打成 pending |

判断仍然只在 `gate.py`,**一行都不用改** —— 客户端把不可达表达成 `suspect` + `verdict=error`,
`gate.unavailable`(`verdict == "error" and replaces_published`)自然就成立了。

## 去重键归门户

门户算自己的键、存自己的库、查自己的记录(`gate.recent_audit`,TTL 600 秒);引擎返回的 `content_sha`
只是"我哈希了什么"的出处证明,两者不需要相等。

曾经设计成"门户把键传给引擎、引擎原样回显",撤回了:那是让引擎替调用方保管状态,凭空造出一个必须
对齐的东西。同理不让两边各留一份哈希算法 —— 算法一改就静默对不上,表现是白跑一次几十秒的审计,没人
会注意到。

**复用不加数据库列。** 早先想加 `cause_owner` 与 `response_json`,都撤了:归属派生而不存(见上),而
复用的保真度用**往返测试**保证(每个字段存进去再读出来必须相等),不用把线上格式塞进库 —— 那会让库
跟着契约版本走。`gate.py` 里已经因为逐字段重建漏过字段(注释仍在),往返测试正是拦这件事的东西。

## 鉴权

- **不发布端口**是网络隔离,不是鉴权:同一 overlay 上任何容器都能连上。
- 鉴权用 Bearer token,而且**两个不同的 token**:门户 → 引擎、引擎 → 判定器。共用一个的话,引擎被
  攻破就等于拿到判定器的额度。
- 判定器现在的实现是**token 为空则完全不校验**。引擎不照抄:**token 为空直接拒绝启动**(本地开发用
  `ALLOW_INSECURE=true`)。
- 鉴权必须在**请求体校验之前**。写成端点参数时 FastAPI 先校验表单,未鉴权的调用方拿到 422 加一份
  字段名清单 —— 鉴权不是第一道闸,还顺带把接口形状告诉了它。所以用中间件,并且用**空请求体**断言 401,
  合法请求体两种实现都能过、测不出区别。
- token 仍会进 service spec(已知弱点,见 platform-ci 的 CUTOVER.md),与现状持平。

## 部署上必须照抄的

| 服务 | 配置 |
|---|---|
| 引擎(无状态) | `replicas: 2` + **`placement.max_replicas_per_node: 1`** + `update_config: start-first` + `failure_action: rollback` + `/health` + **不挂卷**(挂了就把副本钉死在一台机器,写 stdout) |
| 判定器 | `update_config: stop-first` + 钉机器**不变**(kiro 登录卷在那台盘上,两副本同写会坏) |

`max_replicas_per_node` 不是 `preferences`:实测滚动更新之后两个副本都落在了 manager 一台上,
`preferences` 只是偏好。那一台一挂引擎就全没了,两副本是句空话。代价是一台下线时第二个副本会一直
pending 调度不上去 —— 这是想要的,剩下那个照常服务。

超时是两个数,别混:

- **总时限**要大于一次审计的最坏情况(扫描 900 + 判定 200 ≈ 1100 秒)。今天进程内审计也是这个最坏
  情况,不是新增风险。
- **单次读超时**靠 ping 压到一分钟量级,这样引擎挂死一分钟内就暴露。没有 ping 的话读超时只能设到
  1100 秒以上,挂死要等将近二十分钟。

SSE 要带 `X-Accel-Buffering: no`(两层反代之间需要它,否则事件被缓冲住)。

## 这次拆分不解决什么

说清楚,免得被当成高可用方案:

- **判定器仍是单副本、钉机器**(kiro 登录卷),所以**审计链路的可用性上限不变**。
- **后端仍然钉机器**:它被钉住是因为发布路径挂着技能仓工作副本与推送私钥,那部分不在引擎里。要解开
  得做 [repo-access.md](repo-access.md) 那件事。
- 控制面单 manager、入口单 IP,都不变。

拆分真正买到的是:门户镜像卸掉第三方工具链、扫描跑飞不再拖住后端 API、引擎自己可以两副本跨节点、
以及审计的改动不再需要发一次门户版本。

## 顺序

1. **起引擎服务,门户不切过去。**(已完成)测试环境 2 副本,`/health` 200、鉴权 401、真实审计 21 秒
   `pass`/`complete`、五个分析器全部用到(判定器连通)。回退=删服务,门户零改动。
2. **门户改成调用引擎,同一次改动里把扫描器从门户镜像去掉。** 不做开关:开关意味着两条代码路径都要
   维护和验证,而门户仓有 git 历史,回退就是回滚这次改动并重放上一个 tag。
   切之前四条路径在测试环境真跑一遍:`pass`、`suspect`(有复核分支 + MR)、`danger`(拒绝写入)、
   **重发布时引擎不可达 → 503 retry 而不是降级**。另外验:门户镜像里 `skill-scanner` 确实没了;同一
   内容第二次上传走复用且字段不丢。
3. **判定器迁仓单独做**,而且**门户仓移除构建与新仓接手必须同一步** —— 否则 `skill-audit-judge` 镜像
   断产,任何引用新 tag 的部署都会失败。**镜像名与 external 卷名逐字不变**
   (`ai-portal-be_judge-kiro-home` / `..._share`,测试环境 `ai-portal-audit-staging_*`)。改了名字就会
   挂到空卷 → 判定器"未登录" → 全部上传转人工复核。切前先记基线:卷内容、技能条数、审计记录数。
4. **生产**:`deploy/prod/compose.yml` 加引擎服务、`services.txt` 加一行、`env-files.txt` 加一行 +
   新建 `SKILL_AUDIT_PROD_ENV`(含非空 `ENGINE_TOKEN`,缺了部署任务直接 exit 1)。
5. **版本集合**:切换前先 `capture-release` 存一组已知可用的。`SKILL_AUDIT_TAG` 会被自动采集(采集范围
   是描述文件里所有 `${*_TAG}`)。回滚到引擎出现之前的版本集合**不会坏**:`swarm-apply.sh` 对缺席的
   变量保留旧值、从不清空。
