# 把审计拆成独立服务

事实与投影的划分见 [security-compliance.md](security-compliance.md),重复性维度的模型见
[duplication.md](duplication.md)。这一份只讲一件事:审计能力从后端仓拆出去之后,边界画在哪。

## 结论

新仓 `skill-audit`(group `rp-ai-miao`)拥有整个审计能力:引擎 + 判定器,产出两个镜像。引擎是无状态
HTTP 服务。`gate.py` 与 `reconcile.py` **留在门户**。

## 为什么是服务,不是库

- 第三方扫描器 `cisco-ai-skill-scanner==2.0.12` 现在装在**门户主镜像**里(CI input `extra_pip`)。
  扫描器升一个版本要重建并重新部署门户。
- 判定器早就是独立服务,链路今天已经是 门户 → HTTP → 判定器。再加一跳是同一个形状,不是新概念。
- 扫描是重负载(`audit_scan_timeout` 默认 900 秒),今天和请求服务共进程共内存,一次跑飞的扫描会拖
  住后端 API。
- 库省下的只有那一跳网络,而版本一样要钉、接口改一样要两边升。省不到协调成本。

## 边界

**搬走**:`scan` `scanners` `verdict` `pipeline` `report` `types` `acp`(约 1143 行,零数据库引用)、
`skill_audit/policy.yaml`、以及判定器(`app/acp_openai_service.py`、`Dockerfile.judge`、`.kiro/agents`)。

判定器跟着走,因为它是"模型访问能力",只有审计用;而 `acp.py`(客户端)与判定器(服务端)是同一个
协议的两半,同仓才能原子地改契约。搬完门户仓里既没有扫描器也没有 kiro-cli。

**不搬**:`gate.py`(决定 `status`、写审计记录)、`reconcile.py`(从 MR 状态重算投影)。它们讲的是
门户怎么处理审计结论,不是怎么审计。

**引擎不碰技能仓的工作副本**——`app/services/skill_audit/` 里对 `skill_repo_path` 零引用,所以引擎
从第一天就是无状态的,不需要先做别的改造。

## 接口:一个路径,两种表述

```
POST /v1/audits        Accept: application/json      → 同步返回结论(发布路径用)
POST /v1/audits        Accept: text/event-stream     → 先 stage 事件,最后 result(上传界面用)
```

用内容协商而不是两个端点:逻辑只有一份。

**不做"POST 拿任务号,再 GET 查状态"**:那样服务要记住任务状态,而两次请求可能落到不同副本,除非做
粘性路由。一个请求一条连接从头到尾,服务不需要任何任务表,几个副本都能跑。

发布路径要的是结论,不是进度,所以它走 JSON,不必去解析 SSE。

## 失败语义:不能一刀切

`gate.py` 里已经有一条精确的规则,拆分**必须保留**:

> `unavailable` = 审计跑不起来 **且** 内容已经上线 → 调用方什么都不要改,让它重试。
> 别处遇到不可用的判定会转人工复核,那是在提交者身上 fail closed;这里那样做,是在**每一个已经在用
> 这个技能的人**身上 fail closed,而它一分钟前还是好的。

所以:

| 情形 | 处理 |
|---|---|
| 引擎不可达 / 审计没跑起来 | 引擎侧表达为 `verdict=error`(与今天进程内一致) |
| 新提交 + error | 转人工复核 |
| **重新发布已上线内容 + error** | **retry,不降级**。不能把线上好技能因为一次抖动打成 pending |

判断仍然只在 `gate.py`。引擎只报事实(跑了没跑、命中什么),不替门户做生命周期决定。

## 契约不只是类型

跨仓之后,门户与引擎进入两个独立的 sha 空间。今天门户和判定器是**同一个 commit**(版本集合里两个
tag 完全相同),兼容性是结构保证的;拆开后只能靠契约:

- 版本放路径里(`/v1/`),门户校验。
- 契约**包含两个词表**,不只是数据结构:`REVIEW_SIGNAL_CATEGORIES`(`pipeline.py:158`)与
  `INCOMPLETE_RULES`(`scan.py:33`)。引擎改一个类别 id 或规则 id,门户的 `gate` 会**静默误判**。
- 已有的 `tests/test_scanner_contract.py` 要扩到覆盖这条 HTTP 边界。
- 门户侧不共享包,自己保留一份 DTO(约 40 行),用契约测试锁住,而不是靠共用类型。
- 回滚要**成对回**:只回一个仓可能落到不兼容的组合上。

## 重复性维度怎么放

`duplication.md` 定的是:事实是成对关系、追加写;上传时算一次,再由**已有的对帐器**周期重算。拆分后
这条不变,分工是:

- **引擎**:计算。语料由它**自己按 sha 从 GitLab 读技能仓**(只读 token),不由门户喂——"该跟哪些
  技能比"是算法的事,门户不知道。读别人的数据库是另一回事,那是数据层耦合;技能仓是内容的权威存储,
  两个服务都做它的客户端是正当的。
- **门户**:持久化成对事实,并由现有对帐器周期触发。

所以引擎仍然无状态:它不存任何东西,服务内若建索引,那是可重算的派生数据。

## 鉴权

- **不发布端口**是网络隔离,不是鉴权:同一 overlay 上任何容器都能连上。
- 鉴权用 Bearer token,而且**两个不同的 token**:门户 → 引擎、引擎 → 判定器。共用一个的话,引擎被
  攻破就等于拿到判定器的额度。
- 判定器现在的实现是**token 为空则完全不校验**(`acp_openai_service.py`,而 `audit_judge_token` 默认
  空)。引擎不要照抄这一点:**token 为空直接拒绝启动**,否则忘配就等于裸奔。
- token 仍会进 service spec(已知弱点,见 platform-ci 的 CUTOVER.md),与现状持平。

## 部署上必须照抄的

| 服务 | 配置 |
|---|---|
| 引擎(无状态) | `replicas: 2` + `placement.preferences: spread node.hostname` + `update_config: start-first` + `failure_action: rollback` + `/health` + **不挂日志目录**(挂了就把副本钉死在一台机器,写 stdout) |
| 判定器 | `update_config: stop-first` + 钉机器**不变**(kiro 登录卷在那台盘上,两副本同写会坏) |

超时是硬点:**门户 → 引擎的客户端超时必须 ≥ 引擎自己的扫描上限(900 秒)**,否则门户先超时,变成
假的 fail-closed。SSE 要照 `upload_stream.py` 发 `ping` 并带 `X-Accel-Buffering: no`。

## 这次拆分不解决什么

说清楚,免得被当成高可用方案:

- **判定器仍是单副本、钉机器**(kiro 登录卷),所以**审计链路的可用性上限不变**。
- **后端仍然钉机器**:它被钉住是因为发布路径挂着技能仓工作副本与推送私钥,那部分不在引擎里。要解开
  得做 [repo-access.md](repo-access.md) 那件事。
- 控制面单 manager、入口单 IP,都不变。

拆分真正买到的是:门户镜像卸掉第三方工具链、扫描跑飞不再拖住后端 API、引擎自己可以两副本跨节点、
以及审计的改动不再需要发一次门户版本。

## 顺序,每步可回退

1. **起引擎服务,门户不切过去。** 验 `/health`、能连判定器、能读技能仓。回退=删服务,门户零改动。
2. **门户加开关调用引擎,默认关。** 回退=翻开关。
3. **翻开关。** 四条路径都要真实验一遍:`pass`、`suspect`(有复核分支 + MR)、`danger`(拒绝写入)、
   以及**重发布时引擎不可达 → retry 而不是降级**。
4. **稳定之后**才从门户镜像移除扫描器(CI 的 `extra_pip`)。这一步最不可逆:先移除再切,会让每一次
   上传都因为"扫描没跑"落到人工复核。保留上一个门户 tag 以便改 tag 重放回滚。
5. **判定器迁仓单独做**,而且**镜像名与 external 卷名逐字不变**(`ai-portal-be_judge-kiro-home` /
   `..._share`,测试环境是 `ai-portal-audit-staging_*`)。改了名字就会挂到空卷 → 判定器"未登录" →
   全部上传转人工复核。切前先记基线:卷内容、技能条数、审计记录数。
6. **版本集合**:切换前先 `capture-release` 存一组已知可用的;引擎第一次纳入环境要单独部署一次
   (`swarm-apply.sh` 遇到没声明版本的服务会直接拒绝部署)。
